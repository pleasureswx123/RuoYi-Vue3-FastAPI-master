# Shot Grid 业务前端协作指南

## 1. 适用范围与事实基线

本文件适用于 `shot-grid-frontend/` 及其子目录，并继承仓库根目录 `AGENTS.md` 的通用规则。发生冲突时，以本文件为准。

- 产品需求基线：`docs/项目需求规格与业务规则.md`；`docs/需求.md` 保留原始产品构想。
- 基础后端：`../ruoyi-fastapi-backend/`。
- 后台管理端参考实现：`../ruoyi-fastapi-frontend/`。
- 当前主数据库：PostgreSQL。
- 当前目录已有需求、计划和契约文档，但尚未创建可运行的前端工程。后端已建立 PostgreSQL 领域表、迁移链、导航、项目创建/存储状态/成员/范围查询，以及镜头和资产 Excel 预检与正式提交；NAS Worker、项目其余 CRUD、版本发布和审核闭环尚未实现。不得把后端增量、需求设计、静态页面或 Mock 数据描述成已完成业务闭环。

需求文档定义产品意图，本文件补充工程边界和必须保持的数据不变量。若需求文档与已确认的后端契约不一致，应先记录差异，再修改实现；不得在页面组件中用临时兼容掩盖数据模型冲突。

### 1.1 后端基座对齐是强制前置步骤

Shot Grid 的任何需求拆解、表设计、API 设计、前端类型定义和后端实现，都必须先核对 `../ruoyi-fastapi-backend/` 的实际代码与 PostgreSQL 基线。不得先按历史参考或主观习惯完成设计，再在实现阶段补做兼容。

每次开始新的业务增量，至少核对：

1. 对应平台表和 SQLAlchemy DO 的主键、字段类型、审计字段、状态和逻辑删除语义；
2. Pydantic VO 的 snake_case/camelCase 映射、分页模型和统一响应 envelope；
3. `PreAuthDependency`、`UserInterfaceAuthDependency`、`DataScopeDependency` 及业务专用权限依赖的适用边界；
4. `ResponseUtil`、全局异常处理和真实 HTTP 状态的当前行为；
5. `sys_file_info`、`sys_file_reference`、ACL、下载授权和文件事务边界；
6. SQLAlchemy DO、PostgreSQL Alembic revision 和 `sql/ruoyi-fastapi-pg.sql` 的同步交付要求。

执行结论分为三类：

- **完全一致**：直接复用基座契约；
- **兼容扩展**：保留基座 envelope、命名和生命周期，明确新增的异常、权限或业务表能力；
- **当前不一致**：先修订契约或形成经确认的基座升级方案，禁止静默实现。

发生冲突时，以已验证的后端实际行为为当前事实。产品确需改变基座时，必须明确影响范围、迁移方案和验证门禁，并同步更新本文件与 `docs/领域模型与API契约.md`。不得把“设计上可行”表述成“后端已经支持”。

## 2. 项目定位与系统边界

`shot-grid-frontend` 是面向 AI 影视制作成员、项目总监和内部审核人员的独立业务应用，不是第二套系统管理后台。

```text
shot-grid-frontend
  → 登录、项目、镜头、资产、任务、版本、审核、文件业务界面
  → 复用 RuoYi 的认证、用户、权限、字典、文件和传输加密能力
  → 调用 ruoyi-fastapi-backend 的 Shot Grid 业务接口
  → PostgreSQL 持久化业务数据

ruoyi-fastapi-frontend
  → 用户、角色、菜单、字典、参数、文件治理、插件和运维管理
```

必须保持以下边界：

- 后台管理功能继续留在 `ruoyi-fastapi-frontend`，不得把用户、角色、菜单、字典等系统管理页面复制到本应用。
- 本应用应拥有独立的构建产物、路由和业务布局；不得在运行时通过 `../ruoyi-fastapi-frontend/src/...` 深层导入兄弟工程源码。
- 可以复用后台管理端已经验证的实现思路和少量基础代码，但复制后由本应用独立维护，并记录来源及必要差异。
- 后端业务代码不放在本目录。需要新增接口时，放入独立的 Shot Grid 后端业务模块，并遵循后端目录的 `AGENTS.md`。
- Shot Grid 新业务默认只承诺 PostgreSQL。除非用户明确扩大范围，不为该业务模块额外设计或声称 MySQL 兼容。

### 2.1 参考资料使用边界

`参考资料/` 保存的是一个没有当前 RuoYi 基座支撑的历史半成品，只能作为产品和交互参考，不是当前工程的源码基线。

- 可以参考：页面信息架构、影视业务字段、镜头多视图、版本审核布局、导入预览、文件中心交互和异常场景。
- 不得复用：React/Express 技术栈、Context 状态架构、本地账号体系、独立服务端、数据库迁移、路由和构建配置。
- 不得复制其 `package.json`、`server/`、`src/context/`、迁移 SQL 或 LocalStorage/Mock 数据实现到正式工程。
- 所有采用的能力都必须使用本项目的 Vue 3、Pinia、Axios、RuoYi FastAPI、PostgreSQL、Redis、平台权限和受保护文件体系重新设计实现。
- 参考项目中能够展示的页面不代表功能已经完成；其中镜头、资产、任务、版本和审核数据主要仍是 Mock/LocalStorage 状态。
- 参考项目中的部门聊天、外部客户门户和独立管理员账号不进入当前 MVP。
- 采用参考设计前先查看 `docs/参考项目评估.md` 中的“采用、重做、放弃”结论。

## 3. 产品主线与范围

所有功能围绕一条主链设计：

```text
项目
  → 集
  → 场次
  → 镜头或资产
  → 唯一视频或图片任务
  → 不可覆盖的版本
  → 自动审核单
  → 绑定版本的审核意见
  → 退回后新版本，或最终版本并完成任务
```

每次版本提交必须自动创建一个只包含当前版本的审核单；人工批量审核单仍可按顺序组织多个版本，不改变版本原有归属。

第一版主导航固定为六项：

1. 工作台
2. 项目
3. 镜头管理
4. 资产库管理
5. 版本审核
6. 文件与 NAS

任务详情、镜头详情、资产详情和版本审核属于深层业务页面，不增加一级导航。项目内部导航固定为概况、集与场次、镜头、资产、审核、成员。

第一版不建设：

- 自定义实体、字段、页面和状态设计器；
- 复杂甘特图、工时、预算、成本结算和财务模块；
- 完整聊天、在线剪辑和数字资产管理系统；
- Premiere、达芬奇等桌面软件插件；
- 自动同步客户端；
- AI 自动拆剧本、自动审核和自动生成提示词；
- 客户独立门户。

需求中的“客户或外部审核”是后续权限模型的预留能力。MVP 先完成登录用户范围内的内部审核，不得借此扩展出匿名分享或客户门户。

## 4. 核心领域不变量

### 4.1 用户与项目成员

- 用户必须复用 RuoYi 的 `sys_user`，不得再创建一套业务登录账号或独立 `users` 表。
- 全局系统角色与项目内角色是两层概念。管理员来自平台权限；项目总监、制作人员等身份由项目成员关系表达。
- 每个项目必须有明确的成员关系和项目角色。仅在前端隐藏项目入口不构成数据权限。
- 项目必须保存经确认且唯一的项目代号，并直接作为业务文件名前缀；不得再维护一个可与项目代号漂移的 `file_prefix` 业务值。制作任务负责人必须保存当前项目内唯一的制作人缩写；可以提供首字母建议，但不得在每次上传时临时猜测。

### 4.2 镜头、资产与任务

- 集属于且只属于一个项目，场次属于且只属于一个集，镜头属于且只属于一个场次。
- 业务界面可按契约展示集、场次、顺序、镜头号、制作信息、镜头描述、资产关系和审核派生数据；不得把界面展示列误当成 Excel 导入模板。
- 当前镜头 Excel 模板以 `docs/镜头-样表.xlsx` 为准：每个可见 Sheet 表示一集，Sheet 名为 `EP001` 等格式，主数据区为从 A1 开始的 A:P 16 列；Q:R 空白分隔后的辅助区域不得解析。
- 镜头和资产正式提交统一使用 `selectedRows[{sheetName,rowNumber}]`；不能仅传 `rowNumbers`，因为不同 Sheet 的物理行号会重复。预览 Token 只短期存在，前端应保存首次提交使用的幂等键，并允许后端从 PostgreSQL 结果快照重放成功响应。
- “序”固定规范化为 `scene_no=0` 和场次代码 `000`；镜头号在整集内唯一，不能按场次重置；焦段按文本保存以兼容 `35/25` 等组合值。
- “集”和“场次”是父级实体；“场景”和“角色”来自镜头关联的 Environment、Character 资产；成片顺序由样表 Sheet 内有效行顺序派生或在界面维护。
- 制作人、镜头缩略图、当前最新反馈和镜头状态分别从任务、版本文件、审核意见和状态聚合获得，禁止作为可独立修改的重复事实列写入镜头主表。
- 资产属于且只属于一个项目；MVP 资产类型只允许 `Character`、`Environment`、`Prop`，不拆成独立业务模块。
- 未来增加资产类型必须同步数据库约束、后端校验、字典、导入映射、路径规则和测试，不能只新增字典值。
- 一个资产可以包含多个制作分项；制作分项是独立分配、提交版本和审核的最小图片生产单元，保存在 `sg_asset_item`，不放在资产主表。
- 资产表至少包含类型、名称、制作分项、描述、备注、状态、制作人；任务描述、状态和制作人从当前制作分项唯一任务聚合。
- 任务必须且只能属于一个镜头或一个资产制作分项，不能同时属于两者，也不能成为无归属任务。
- 每个镜头最多一个 `shot_video` 任务，每个资产制作分项最多一个 `asset_image` 任务；首次分配主制作人时创建，改派时更新同一任务。
- 制作分项允许在资产导入时为空，只返回警告并允许后续补充；资产图片版本提交前必须补齐。每个制作分项只允许一名主制作人，复合制作人文本必须作为导入错误处理。
- 图片和视频在线下制作，平台只负责收任务、上传产出物、生成版本、自动创建审核单和记录审核结果，不实现在线生成或剪辑。

### 4.3 版本与审核

- 版本必须属于一个任务，镜头或资产归属通过任务推导，不重复维护互相冲突的归属字段。
- 版本号由后端在事务中分配，并在任务范围内唯一；前端不得通过列表长度计算下一个版本号。
- 已提交版本不可覆盖。修订必须创建新版本，历史版本的媒体、生成参数、提交人和提交时间保持可追溯。
- 审核意见必须绑定具体版本；视频意见使用确定的时间点，图片或视频标注使用归一化坐标。
- “确认通过”“退回修改”“稍后决定”是不同业务动作，不得只改一个展示标签。
- 确认通过并设置最终版本必须由后端在同一事务内完成，并处理并发审核；同一任务同时只能有一个最终版本。
- 审核单与版本是有序多对多关系，关系记录必须保存顺序，不得依赖前端数组的偶然顺序。
- 上传平台受保护文件不等于版本成功。必须通过 `sg_version_submission` 完成 NAS 临时写入、摘要校验和原子改名，再在短数据库事务中创建正式版本、文件引用、`auto_single` 审核单并把任务改为待审核。退回后再次上传必须生成新版本和新审核单，不能覆盖旧记录。

### 4.4 文件

- 文件必须通过现有受保护文件体系上传和下载，业务数据保存稳定的 `fileId`，不得保存临时 Blob URL 或把本机绝对路径当作下载地址。
- 审核文件与源文件是用途分类，不是两套脱离业务引用的存储系统。
- 版本可以关联多个文件，并明确主审核文件、缩略图、代理文件、原始生成文件、修复后文件或源文件等用途。
- 主产出物业务文件名按 `docs/领域模型与API契约.md` 生成并保存在 `sg_version_file.business_file_name`；不得改写平台 `stored_name` 或 `storage_key`。
- 镜头主产出物业务文件名固定为 `{项目缩写}_EP{集号至少3位}_{场次号至少3位}_S{镜头号至少3位}_{制作人缩写}_V{版本号至少3位}_{服务端毫秒时间戳}.{mp4|mov}`，例如 `WGZR_EP001_001_S001_YJF_V001_1786094626499.mp4`。文件名版本号必须与正式版本记录一致。
- 资产主产出物业务文件名固定为 `{项目缩写}_Asset_{Character|Environment|Prop}_{资产名称}_{制作分项}_{制作人缩写}_V{版本号至少3位}_{服务端毫秒时间戳}.{jpg|png}`，例如 `WGZR_Asset_Environment_动力舱室内_动力舱恐怖气氛主视角_YJF_V001_1786094626499.jpg`。资产名称和制作分项都必须安全规范化，且制作分项取任务所属 `sg_asset_item` 的稳定值。
- 镜头和资产文件名使用的版本号与服务端毫秒时间戳都只能生成一次；同一幂等请求必须复用已生成值和业务文件名。
- 镜头任务只接受 MP4/MOV，资产任务只接受 JPG/PNG；后端必须校验实际内容类型。
- 缩略图、转码、代理文件和媒体元数据属于后端或异步处理能力；前端不得用占位地址假装处理成功。
- 浏览器通常不能可靠直接打开 UNC/NAS 路径。MVP 应提供查看和复制路径；只有存在已确认的桌面协议处理器时才能提供“打开 NAS”。
- NAS 根目录只能来自管理员白名单。项目创建必须同时写入项目存储绑定和目录 Outbox；项目存储为 `ready` 前不得进入正式业务写入。
- 平台权限不能约束用户绕过网页直接访问 SMB 共享；部署必须单独配置 NAS/AD/Windows 共享 ACL，并明确平台外直接访问边界。
- 页面卸载后必须释放 `URL.createObjectURL` 创建的临时资源，禁止把大文件或 Base64 媒体长期存入 Pinia、LocalStorage 或 SessionStorage。

## 5. PostgreSQL 数据契约

需求文档列出的九张表是概念清单，不是完整可实施的数据库设计。后端落库时使用 `sg_` 前缀避免与平台表冲突，并至少覆盖：

- `sg_project`
- `sg_project_member`
- `sg_episode`
- `sg_scene`
- `sg_shot`
- `sg_asset`
- `sg_asset_item`
- `sg_shot_asset`
- `sg_task`
- `sg_version`
- `sg_version_file`
- `sg_note`
- `sg_note_reply`
- `sg_review_action`
- `sg_review_list`
- `sg_review_list_version`
- `sg_storage_root`
- `sg_project_storage`
- `sg_storage_operation`
- `sg_version_submission`
- `sg_import_batch`
- `sg_shot_asset_requirement`

用户引用 `sys_user.user_id`。文件复用平台文件表和业务引用机制，不重复建设文件主表；`sg_version_file` 只补充版本文件的用途、主文件和顺序，并必须同步维护平台业务引用。

镜头和资产导入必须保持以下不变量：

- 正式顺序是创建项目、导入镜头表、再导入资产表；不得在实现中重新要求用户先创建全部资产。
- 镜头导入按去重业务键创建集、场次和镜头，不以 Excel 行数保存统计值。
- 当前镜头样表只有“场景”资产列：尚不存在的场景只创建 `Environment` 类型的 `sg_shot_asset_requirement`，不得隐式创建正式资产或资产任务；不得从描述、台词或备注猜测角色和道具。
- 资产导入后只按项目、资产类型和统一规范化名称匹配唯一候选；无候选保持待匹配，候选不唯一进入冲突，不能静默选第一条。
- 镜头和资产导入都必须经过预检查、短期 Token、正式提交、数据库重新校验和幂等保护；禁止前端逐行调用 CRUD 接口落库。
- 选中批次任一行失败时，集、场次、镜头、资产、任务、关系、待匹配需求和目录 Outbox 必须全部回滚。

数据库实现必须满足：

- 项目内集号、集内场次号、集内镜头号和必要业务编码具有明确唯一约束。
- 任务通过 PostgreSQL `CHECK` 约束保证镜头归属和资产归属二选一。
- 数据库部分唯一索引保证每个镜头或资产制作分项最多一个正式任务。
- 版本在任务范围内具有唯一序号。
- 版本提交必须同时生成不可变业务文件名和自动单版本审核单。
- 审核单版本关系在审核单内具有唯一顺序。
- 项目、任务、版本、审核意见等关键表具有创建人、创建时间、更新人和更新时间等审计字段。
- 高频查询至少评估项目、集、场次、状态、负责人、截止日期、任务、审核状态和创建时间索引。
- 时间字段与后端基座保持一致：SQLAlchemy 使用 `DateTime`，PostgreSQL 使用 `timestamp(0) without time zone`。
- `del_flag = '2'` 只表示逻辑删除；业务归档使用明确状态字段，归档后保持 `del_flag = '0'`。
- 结构升级同时提交 SQLAlchemy DO、PostgreSQL Alembic 迁移和 `ruoyi-fastapi-backend/sql/ruoyi-fastapi-pg.sql`，不依赖 `create_all()` 修改已有表。

业务 API 统一使用 `/shot-grid` 前缀，权限码统一使用 `shotgrid:<resource>:<action>` 形式。若后端已有不同的正式契约，以已提交接口为准，并同步修订本文件和需求说明。

## 6. 前端技术基线

`shot-grid-frontend` 的技术栈、核心依赖版本、构建方式和基础工程组织以 `../ruoyi-fastapi-frontend/` 为首要参考；初始化或升级依赖前先核对其 `package.json`、Vite 配置和现有基础设施，未经用户明确批准不得另起一套前端技术体系。

初始化工程时默认沿用后台管理端已使用的技术栈：

- Vue 3
- Vite
- Vue Router
- Pinia
- Axios
- Element Plus
- Sass
- npm

除非用户明确批准技术迁移，不引入 React、Nuxt、另一套组件库或另一种包管理器。新工程必须提交 `package-lock.json`，保证依赖安装可复现。

优先复用或适配后台管理端的以下能力：

- 登录、Token 获取和退出逻辑；
- `src/utils/request.js` 的统一 Axios 实例；
- 传输加密、401 处理、错误码和二进制下载逻辑；
- 用户信息和权限加载；
- `BusinessFileUpload` 的 `fileId` 业务引用契约；
- 基础布局、图标、字典和通用格式化工具。

不得绕过统一请求层自行创建不带认证、错误处理或传输加密的 Axios 实例。上传、下载或流媒体接口需要排除应用层加密时，应与后端协议共同确认，不能在单个页面私自关闭安全策略。

## 7. 推荐目录与依赖方向

创建源码后优先采用以下结构：

```text

├─ docs/
├─ public/
├─ src/
│  ├─ api/shot-grid/
│  ├─ assets/
│  ├─ components/
│  │  ├─ media/
│  │  ├─ review/
│  │  └─ version/
│  ├─ layout/
│  ├─ router/
│  ├─ store/modules/
│  ├─ utils/
│  └─ views/
│     ├─ workbench/
│     ├─ project/
│     ├─ shot/
│     ├─ asset/
│     ├─ task/
│     ├─ review/
│     └─ file/
├─ package.json
```

依赖方向保持：

```text
路由页面
  → 领域组件
  → Pinia（仅共享状态）
  → 领域 API
  → 统一 request
```

- API 按项目、镜头、资产、任务、版本、审核单和文件分域，不把所有接口写进一个文件。
- 页面不直接拼接后端 URL、权限码、状态颜色和状态中文名称。
- Pinia 保存身份、项目上下文、轻量筛选条件和必要缓存，不保存组件局部表单、媒体二进制和超大列表。
- 表格、卡片和故事板是同一查询结果的不同视图，不得各自维护一套互相漂移的数据。
- 媒体播放器、标注画布、A/B 对比等重组件按路由或功能懒加载。

## 8. 路由、认证与权限

MVP 的认证与部署边界已经冻结：

- 管理端部署在 `/admin/`，Shot Grid 部署在 `/shot-grid/`，两者是同一 Origin 下的独立 SPA 和独立构建产物；`/api/` 统一反向代理到同一个 RuoYi FastAPI 实例。
- Shot Grid 提供自己的业务风格登录页，但只复用平台 `POST /login`、`GET /getInfo`、`POST /logout` 和 Bearer Token 协议；不得新增认证服务、JWT 规则或业务账号表。
- 两个应用共享 Cookie 键 `Admin-Token`，Cookie `Path=/`。任一应用主动退出或确认处理 401/Token 过期时，必须调用平台退出接口并清除此键，因此两个应用同时退出；跨应用跳转不复制、不把 Token 放入 URL，目标应用直接读取共享 Cookie 并以 `GET /getInfo` 恢复身份。
- 共享键意味着任一前端发生 XSS 都可能影响两个应用的会话。MVP 只允许同域、同信任边界部署；不得把 Shot Grid 放到第三方托管页面或降低 CSP、依赖审计等安全门禁。未来若拆分信任边界，应改为不同 Cookie 键并分别登录，不能在两个前端间传递明文 Token。
- Shot Grid 必须独立维护与管理端等价的统一请求、认证和传输加密适配，不得运行时深层导入管理端源码。实现时逐项对齐 `request.js` 的 Bearer/401 行为、`auth.js` 的 Cookie 语义、`transportCrypto.js` 的 AAD 路径规范化和密钥刷新、`permission.js` 的刷新恢复逻辑。
- API 前缀冻结为：本地开发 `/dev-api`，生产 `/api`，Docker `/docker-api`。代理必须剥离浏览器侧前缀再转发；后端单实例的 `APP_ROOT_PATH` 必须与对外 API 前缀一致，不能让管理端和 Shot Grid 以两个不同 root path 直连同一实例。详见 `docs/部署说明.md`。

建议业务路由至少覆盖：

```text
/workbench
/projects
/projects/:projectId/overview
/projects/:projectId/scenes
/projects/:projectId/shots
/projects/:projectId/assets
/projects/:projectId/reviews
/projects/:projectId/members
/shots/:shotId
/assets/:assetId
/tasks/:taskId
/versions/:versionId/review
/files
```

- 路由参数进入 API 前必须校验，不能只依赖 TypeScript 或组件 Props。
- 登录和用户信息必须按上述冻结方案复用 `/login`、`/getInfo` 等平台接口。
- 不得直接把后台管理端 `/getRouters` 返回的全部管理菜单加载到业务应用。业务端使用 `/shot-grid/navigation` 获取 `route_name='ShotGrid'` 根节点下的范围菜单，并只通过本地白名单解析稳定路由键。
- 前端路由守卫和按钮权限只改善用户体验；项目成员、资源归属和动作权限必须由后端逐接口校验。
- 后端项目权限必须在平台接口权限之外增加项目成员、项目角色和资源归属校验；现有部门型 `DataScopeDependency` 不能代替项目成员关系。
- 项目切换后必须清理上一个项目的列表、筛选、审核草稿和媒体缓存，防止跨项目数据残留。
- 外部审核未来应采用可撤销、限时、限定审核单的授权模型，不得复用内部管理员 Token，也不得暴露提示词、成本和内部讨论。

## 9. 状态、时间点与批注协议

状态在接口中使用稳定英文代码，中文只作为展示文案。禁止将“制作中”“待审核”等中文直接作为数据库和流程判断值。

建议在正式接口契约中集中定义：

- 任务状态：`not_started`、`in_progress`、`pending_review`、`revision`、`completed`
- 版本状态：`pending_review`、`rejected`、`final`
- 镜头/资产聚合状态：由后端根据任务计算，不提供普通成员手动修改接口

媒体审核协议必须明确：

- 时间点统一保存整数毫秒，不保存格式化字符串作为计算依据。
- 标注坐标按媒体自然尺寸归一化到 `0..1`，同时记录标注类型、颜色、点集和创建时的媒体尺寸。
- 每条批注绑定 `versionId`；切换版本后不得继续提交到旧版本。
- 拖动进度、绘制标注和输入文字属于本地草稿，用户明确提交后才创建审核意见。
- 对无权限查看 AI 参数或费用的用户，后端响应即应裁剪字段，不能只用 CSS 隐藏。

## 10. 交互与视觉原则

- 本应用是制作工作台，不照搬传统后台的“每页一个 CRUD 表格”。
- 镜头页是第一核心页面，必须支持稳定筛选、分页、表格/卡片/故事板切换和项目上下文。
- 审核页是第二核心页面，媒体、版本带、审核意见和确认通过、退回修改、稍后决定三个审核动作应保持在同一工作流内。
- 任务详情应聚合制作要求、依赖、相关资产、历史版本和审核意见，减少跨页面寻找资料。
- AI 生成参数默认折叠；普通审核路径优先展示画面、版本差异和修改说明。
- 所有列表和详情必须具备加载、空数据、失败、无权限和重试状态，不能只实现成功状态。
- 桌面端为第一优先级，但常用操作不得依赖仅鼠标悬停才能发现；键盘焦点、表单标签和颜色对比应可用。
- 长列表使用服务端分页或虚拟化；搜索和筛选需要防抖，并取消已经过期的请求。

## 11. API 与错误处理

- 遵循现有后端统一响应协议，不在每个页面重复解析 `code`、`msg` 和 `data`。
- Shot Grid 领域错误使用稳定 `errorKey`；真实 HTTP 409 等状态由专用领域异常处理器生成，不能直接用默认返回 HTTP 200 的 `ServiceException` 冒充。
- 列表查询的分页字段、排序字段和筛选字段应形成统一约定；禁止同类页面使用不同命名。
- 任何创建、提交和审核操作都要防止重复提交。
- 对 401、403、404、409、413、416 和 5xx 提供可区分的处理：
  - 401：会话失效；
  - 403：无项目或动作权限；
  - 404：资源不存在或已删除；
  - 409：版本号、状态流转或并发审核冲突；
  - 413：上传文件超过限制；
  - 416：媒体 Range 请求无效；
  - 5xx：服务异常，不得伪装成空数据。
- 页面卸载、项目切换和筛选变化时取消过期请求，避免旧响应覆盖新上下文。
- Mock 只用于独立 UI 开发；接入真实接口后不得保留“请求失败自动回退到 Mock”的生产逻辑。

## 12. 安全与隐私

- 不在前端源码、环境文件、日志、错误提示或测试快照中保存真实密码、Token、Provider Key、私钥和内部 NAS 凭据。
- 评论、文件名、提示词和项目描述均按不可信输入处理；渲染富文本时必须经过白名单清洗。
- 文件预览和下载必须使用受保护接口，不泄露 `storage_key`、服务器绝对路径或对象存储凭据。
- 项目搜索和文件搜索必须受项目成员关系与数据权限约束。
- 审核动作、最终版本变更、文件下载和权限变更应由后端记录审计。
- 前端不得根据隐藏字段、路由来源或本地缓存推断授权。

## 13. 实施顺序

按以下顺序推进，未完成前一层真实契约时，不把后一层静态页面描述为完整功能：

1. **应用基座**：工程脚手架、登录、用户信息、统一请求、传输加密、业务布局和基础错误页。
2. **项目骨架**：项目、项目成员、集、场次、镜头和资产的真实列表与详情。
3. **任务链**：镜头视频任务、资产图片任务、负责人和状态流转。
4. **版本链**：受保护文件上传、业务文件命名、版本创建、自动审核单、历史版本、缩略图和媒体播放。
5. **审核链**：版本批注、退回再提交、最终确认和并发冲突处理。
6. **审核单**：有序版本列表、连续审核和内部审核流程。
7. **视图完善**：镜头卡片/故事板、全局搜索、文件页和体验优化。

每一步都应先定义 API 与状态契约，再实现页面；不要以大量硬编码 Mock 页面倒逼后端迁就临时字段。

## 14. 验证与验收

初始化工程时至少提供以下 npm scripts：

```json
{
  "scripts": {
    "dev": "vite",
    "build:prod": "vite build",
    "lint": "...",
    "test": "..."
  }
}
```

Windows PowerShell 下使用 `npm.cmd`。具体脚本以最终 `package.json` 为准，不得在脚本尚不存在时声称命令已通过。

最低验证层次：

- 纯函数和状态映射：单元测试；
- Pinia、路由守卫和核心组件：组件测试；
- API 契约：覆盖成功、无权限、冲突、超限和服务失败；
- 关键链路：使用真实前端、后端、PostgreSQL、Redis 和受保护文件接口进行 E2E。

MVP 不能只以页面数量验收，至少需要真实走通：

```text
登录
→ 创建项目并添加成员
→ 导入镜头表并按去重键创建集、场次、镜头和待匹配资产需求
→ 导入三类资产并完成唯一自动匹配，冲突进入人工处理
→ 分配镜头或资产制作分项并创建唯一任务
→ 在线下制作后上传审核文件，自动形成 V001、规范业务文件名和审核单
→ 退回后上传 V002，V001及其审核单保持不变
→ 对指定版本添加时间点或画面批注
→ 审核确认 V002 为最终版本并完成任务
→ 人工批量审核单保持版本顺序
→ 刷新页面后数据、权限和媒体仍正确
```

还必须覆盖以下负向场景：

- 非项目成员不能读取项目资源；
- 制作人员不能执行总监审核动作；
- 导入批次失败不能留下半成功业务数据，重复幂等键不能重复创建镜头、资产或关系；
- 不存在资产时不能由镜头导入隐式创建正式资产，候选冲突不能静默自动匹配；
- 重复提交不会创建重复版本；
- 两人并发设置最终版本时保持唯一结果；
- 无归属文件、跨项目引用、重复正式任务和错误媒体类型被拒绝；
- 大文件超限、Range 错误、媒体处理失败有明确反馈；
- 页面刷新、项目切换和登录过期不会泄露上一个项目的数据。

构建成功只证明静态产物可生成，不等于上述业务链路通过。

## 15. 变更纪律

- 修改需求范围、核心状态、路由、权限码、API 字段或数据库关系时，先同步更新正式基线 `docs/项目需求规格与业务规则.md` 和 `docs/领域模型与API契约.md`；`docs/需求.md` 仅保留原始产品构想。
- 新增大依赖前说明用途、包体影响和替代方案；媒体与标注能力优先按需加载。
- 不在一次变更中同时完成脚手架、全量业务页面、后端表结构和全部 E2E；按主链拆分可审查、可验证的增量。
- 保留用户已有设计和文档，不因生成脚手架覆盖 `docs/` 或本文件。
- 汇报时明确区分：静态原型、Mock 可交互、真实 API 已接入、集成测试通过、完整 E2E 通过。

## 16. 已确认的独立请求层契约

- Shot Grid 已在 `src/utils/` 独立维护认证 Cookie、统一 Axios 请求、传输加密策略与 RSA-OAEP/AES-256-GCM 信封实现，不运行时导入管理端源码。
- 认证仅接入平台 `/login`、`/getInfo`、`/captchaImage`、`/logout`，业务端不调用 `/getRouters`。
- `/common/download`、`/common/download/resource`、`/common/files/`、`/system/file/download/`、Shot Grid 文件/媒体二进制接口以及带 `Range` 的请求排除应用层加密；请求仍携带 Bearer Token，业务接口还需由后端校验项目权限。
- 传输密钥失效只允许刷新后重试一次；并发 401 只执行一次提示与退出清理。401 清理 Token、身份权限、项目上下文和媒体临时状态。
- 请求层必须区分 401、403、404、409、413、416 与 5xx，服务错误保持 rejected 状态，不得回退为空列表。
