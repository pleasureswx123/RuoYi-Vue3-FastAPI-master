# Shot Grid MVP 部署说明

## 0. 构建环境与依赖安装

发布基线使用 **Node.js 20.20.2** 和 **npm 11.4.2**。`package.json` 与
`package-lock.json` 是同一份依赖契约；发布机和 CI 必须在
`shot-grid-frontend/` 目录使用锁文件进行干净安装：

```bash
rm -rf node_modules
npm ci
npm run lint
npm test
npm run build:prod
```

`lint`、`test` 和 `build:prod` 必须作为三个独立命令执行。生产构建产物位于
`shot-grid-frontend/dist/`，发布时将该目录部署到站点的 `/shot-grid/` 路径。

当前直接依赖版本已经在 manifest 与锁文件中对齐：Axios 1.19.0、Vue
3.5.26、Element Plus 2.14.3、Pinia 3.0.4、Vue Router 4.6.4、Vite
6.4.3，以及 Sass 实现 `sass-embedded` 1.97.2。不得仅修改其中一个文件；
依赖升级后应重新生成锁文件并再次执行 `npm ci` 验证。

### 0.1 npm 代理配置

npm 支持标准的 `HTTP_PROXY`/`HTTPS_PROXY` 环境变量，也可以使用 npm 的
`proxy` 与 `https-proxy` 配置项。例如：

```bash
npm config set proxy http://proxy.example.internal:8080
npm config set https-proxy http://proxy.example.internal:8080
```

若通过环境变量注入 npm 配置，请使用 `npm_config_proxy` 和
`npm_config_https_proxy`。不要使用已失效的 `npm_config_http_proxy`；npm
11 会将它解析为未知的 `http-proxy` 配置并输出
`Unknown env config "http-proxy"`。该变量通常来自 CI、容器或终端启动脚本，
应在相应环境配置中删除，而不是写入项目 `.npmrc`。可用以下命令定位来源：

```bash
env | grep -iE '(^|_)npm.*proxy|^https?_proxy'
npm config list --long
```

## 1. 已冻结拓扑

MVP 采用**同域、不同路径、同一后端**：

```text
https://example.internal/admin/      -> 管理端独立 SPA
https://example.internal/shot-grid/  -> Shot Grid 独立 SPA
https://example.internal/api/        -> 同一个 RuoYi FastAPI 后端
```

两个前端拥有独立入口、路由基址和构建产物，不互相导入运行时代码。Shot Grid 自带登录页面，但认证能力完全复用平台 `/login`、`/getInfo`、`/logout`、Redis 会话与 Bearer Token；不部署第二个认证服务，不创建业务账号表。

## 2. 会话决策

| 项目 | MVP 决策 |
| --- | --- |
| 存储 | `js-cookie` Cookie `Admin-Token`，`Path=/`，两个 SPA 共享 |
| 请求 | `Authorization: Bearer <Admin-Token>` |
| 刷新 | 读取 Cookie，调用 `/getInfo`，成功后恢复原目标路由 |
| 主动退出 | 调用 `/logout`，无论响应结果均清 Cookie 与应用内身份缓存 |
| 401/过期 | 合并并发提示；用户确认后执行同一退出清理，回本应用登录页 |
| 跨应用跳转 | 仅普通同域链接；URL、查询串、fragment、`postMessage` 均不携带 Token |

由于当前 Cookie 不是 HttpOnly，共享会话扩大了两个 SPA 的共同 XSS 影响面。因此该方案只适用于同一组织控制、相同安全等级的同域应用；两套静态资源必须执行相同 CSP、依赖审计和发布门禁。若未来业务端成为不同信任边界，必须改为不同存储键并独立登录，不能用前端脚本交换 Token。

## 3. API 前缀矩阵

| 环境 | 页面入口 | 浏览器 API 前缀 | 后端 `APP_ROOT_PATH` | 代理行为 |
| --- | --- | --- | --- | --- |
| 开发 | Vite 各自端口 | `/dev-api` | `/dev-api` | Vite 剥离 `/dev-api` 后转发 |
| 生产 | `/admin/`、`/shot-grid/` | `/api` | `/api` | Nginx 剥离 `/api` 后转发 |
| Docker | `/admin/`、`/shot-grid/` | `/docker-api` | `/docker-api` | Nginx 剥离 `/docker-api` 后转发 |

**强制不变量：**浏览器所见路径、FastAPI `root_path` 和代理转发路径必须形成唯一、可验证的映射。代理剥离外部前缀后把真实路由转发给应用，`APP_ROOT_PATH` 则声明被剥离的外部前缀，供 OpenAPI、鉴权与传输加密路径规范化使用。不得既保留前缀转发又让应用按无前缀路由注册，也不得重复剥离。同一个后端实例只有一个 `APP_ROOT_PATH`，所以两个前端不能使用不同的 API 前缀访问该实例。

领域路由始终是后端 `/shot-grid/...`；例如生产浏览器请求 `/api/shot-grid/projects`。登录为 `/api/login`。公开传输加密接口为 `/api/transport/crypto/frontend-config` 和 `/api/transport/crypto/public-key`。

## 4. Nginx 参考配置

```nginx
location /admin/ {
    alias /usr/share/nginx/html/admin/;
    try_files $uri $uri/ /admin/index.html;
}

location /shot-grid/ {
    alias /usr/share/nginx/html/shot-grid/;
    try_files $uri $uri/ /shot-grid/index.html;
}

location /api/ {
    proxy_pass http://ruoyi-backend:9099/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

生产后端设置 `APP_ROOT_PATH=/api`。Docker 将上例的 `/api/` 同步替换为 `/docker-api/`，并设置 `APP_ROOT_PATH=/docker-api`。`proxy_pass` 末尾的 `/` 用于剥离 location 前缀，必须保留。

## 5. Swagger 与传输加密核对

部署后逐项检查：

- Swagger、ReDoc、OpenAPI 分别能通过 `{API_PREFIX}/docs`、`{API_PREFIX}/redoc`、`{API_PREFIX}/openapi.json` 访问，生成的 Server URL 不重复也不遗漏前缀。
- `/transport/crypto/frontend-config` 和 `/transport/crypto/public-key` 经同一 API 前缀匿名访问，限流和缓存仍生效。
- Shot Grid 的传输加密实现对齐管理端：在请求参数拼接前加密；AAD 中的 path 是移除外部 API 前缀后的真实后端路径；加密错误响应先解密；公钥失效只清缓存并重试一次。
- 登录、上传、下载和二进制接口继续遵守后端公开策略及排除规则，不能由 Nginx 单独改写业务路径绕过策略匹配。

## 6. 生产配置与秘密注入

生产环境的数据库密码、Redis 密码、`JWT_SECRET_KEY`、传输加密 RSA 私钥和 NAS/SMB
凭据必须由部署平台在运行时注入（例如 Kubernetes Secret、systemd
`EnvironmentFile` 配合严格文件权限，或等价的企业秘密管理服务），不得写入镜像、静态前端、
Nginx 配置、Git 跟踪文件、命令行参数或发布日志。NAS 数据库记录中的 `credential_ref` 只能保存
凭据引用；Worker 由专用最小权限服务身份取得真实凭据。生产密钥必须区别于仓库示例值，
`JWT_SECRET_KEY` 在所有后端实例间保持一致，RSA 私钥轮换必须保留匹配的 `kid` 和兼容窗口。

发布前对当前工作树、完整 Git 历史和待发布产物分别执行秘密扫描。扫描器和规则由组织安全基线指定；
以下命令只是门禁调用示例，不能用普通关键字搜索代替专业扫描，也不得将扫描命中的秘密原文贴入工单：

```bash
gitleaks protect --source . --staged --redact
gitleaks detect --source . --log-opts="--all" --redact
gitleaks detect --no-git --source shot-grid-frontend/dist --redact
gitleaks detect --no-git --source /path/to/backend-image-export --redact
```

只要当前版本、历史提交或构建产物发现真实秘密，就停止发布，先撤销/轮换秘密，再按安全流程清理
历史并重新构建；仅删除当前文件不代表历史或旧产物已经安全。浏览器可下载的前端产物中不得出现任何
服务端秘密。

## 7. 数据库交付路径

Shot Grid 当前只以 PostgreSQL 作为生产验收基线。部署前先记录 `SELECT version()`、
`SELECT current_database()`、`SELECT version_num FROM alembic_version` 和备份校验结果。
仓库当前没有能从空库创建全部平台表的 Alembic baseline，因此必须按库的来源选择且只选择一条路径：

### 7.1 真正的新数据库

使用与发布提交同步的 `ruoyi-fastapi-backend/sql/ruoyi-fastapi-pg.sql` 一次性建立平台与
Shot Grid 最新结构；脚本同时写入对应 Alembic head。不要先运行 Shot Grid 增量 migration 来猜测建立
平台表。导入后运行 `alembic current` 和 `alembic heads`，两者必须一致，再执行约束与集成验证。

```bash
cd ruoyi-fastapi-backend
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/ruoyi-fastapi-pg.sql
alembic current
alembic heads
```

### 7.2 已有、且 Alembic 版本可信的平台库

先做可恢复的 PostgreSQL 物理备份或 `pg_dump`，在维护窗口停止写流量，确认当前 revision 位于仓库已知
迁移链，再执行增量迁移。迁移必须在克隆库演练并记录耗时、锁影响和恢复耗时。

```bash
cd ruoyi-fastapi-backend
alembic current
alembic history --verbose
alembic upgrade head
alembic current
```

### 7.3 历史无版本库

若已有平台或 22 张 `sg_` 表但没有可信 `alembic_version`，**不得直接在正式库执行 `stamp`**。
必须先停止写入并完成可恢复备份，将备份恢复为隔离克隆库，逐表核对字段、约束、索引、数据冲突和
Shot Grid 01 结构。在克隆库确认确实等价后，才可按审定的起点（Shot Grid 旧 01 结构对应
`20260810_01`）执行 `alembic stamp <审定版本>` 和 `alembic upgrade head`，跑完数据库集成测试后
才将同一流程用于生产。无法证明等价时，应制定显式修复/导入方案，而不是用 `stamp` 跳过验证。

## 8. 固定部署顺序与切换

每一步失败都停止后续步骤；尚未切流的旧版本保持运行。推荐顺序如下：

1. **冻结发布与备份**：记录 Git commit、镜像 digest、前端产物摘要、数据库 revision 和回滚负责人；
   暂停会产生业务写入的入口和旧 NAS Worker，完成 PostgreSQL 备份及恢复抽检。
2. **PostgreSQL**：启动/确认目标版本与持久化卷，按第 7 节选择初始化或增量迁移路径，验证 head、
   约束和读写；迁移未通过不得启动新后端。
3. **Redis**：启动/确认持久化、认证、网络 ACL 和容量；使用部署注入的密码验证 `PING`，确认后端各
   实例访问同一预期逻辑库。Redis 不可用时，认证会话、限流、缓存、调度协调和传输防重放均不得
   假装可用。
4. **后端**：注入生产配置，先执行第 9 节诊断，再滚动启动 FastAPI；一个实例通过只表示该实例存活，
   全部实例配置与数据库 revision 一致后才能继续。
5. **NAS Worker**：使用独立最小权限服务身份和唯一 `--worker-id` 启动独立进程；确认数据库、受保护
   上传目录及指定 SMB/NAS 根可访问，再恢复队列消费。不得把 Worker 临时线程塞入 Web 进程。
6. **前端**：将管理端与 Shot Grid 的不可变、带版本目录上传完整，核对摘要后再原子切换
   `current` 软链接或等价版本指针；不要覆盖正在服务的目录。
7. **Nginx**：先 `nginx -t`，再 reload；验证 `/admin/`、`/shot-grid/` 的 fallback 互不串站，
   `/api/` 只剥离一次且代理到本次后端。最后恢复写流量并执行第 12 节冒烟。

NAS Worker 的参考启动命令如下；每个进程的 ID 必须唯一且不得包含主机凭据：

```bash
cd ruoyi-fastapi-backend
python module_shot_grid/storage_worker.py --worker-id sg-storage-prod-01 --idle-seconds 1
```

## 9. 启动前诊断门禁

`app doctor` 已检查数据库连通性、Redis 连通性和传输加密配置，但不能覆盖下面全部业务前置条件。
每次后端或 Worker 启动前都要保存脱敏结果，并补齐人工/自动检查：

```bash
cd ruoyi-fastapi-backend
ruoyi app doctor --env=prod --output=json
alembic current
alembic heads
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -c 'select version(), current_database();'
redis-cli --tls -u "$REDIS_URL" --no-auth-warning PING
```

| 检查项 | 放行条件 | 失败处理 |
| --- | --- | --- |
| 数据库版本 | PostgreSQL 版本受支持；`current` 与本次仓库唯一 `head` 一致；目标 schema 可读写 | 禁止启动新后端/Worker，恢复旧版本或完成迁移 |
| Redis | 认证、TLS/网络、目标逻辑库与 `PING` 正常，容量和淘汰策略符合会话要求 | 禁止切流；不得退化为进程内会话 |
| 防重放 | 生产传输加密模式符合批准值；RSA key/`kid` 有效；用同一 nonce 重放加密请求时第二次被拒绝；`required` 模式下断开 Redis 必须失败关闭 | 禁止降低为明文或绕过中间件 |
| 存储根目录 | 每个启用根的协议、健康状态、挂载/UNC、最小权限服务身份和可写范围通过；路径解析不能逃逸根目录 | 停止 Worker，不能用临时本地目录冒充 NAS |
| Worker 身份 | 每个进程的 `--worker-id` 唯一、不含秘密；OS 服务身份与 `credential_ref` 对应且权限最小 | 修正身份后重启，不允许共享 Worker ID |
| 上传与临时目录 | `UPLOAD_PATH`、`PRIVATE_UPLOAD_PATH` 和系统临时目录存在、属主正确、容量/配额充足且不可被 Nginx 公开；NAS 发布临时文件与目标位于同一文件系统以支持原子 rename | 禁止接收上传或消费发布任务 |
| 必要密钥 | 数据库/Redis/NAS 凭据、固定且足够强的 `JWT_SECRET_KEY`、当前 RSA 私钥由 Secret 注入；多实例值一致，文件权限受限 | 禁止使用空值、默认值、示例值或临时随机 JWT Secret |

诊断证据只能记录状态、版本、引用名和脱敏摘要，不能记录连接串密码、Token、私钥、完整 UNC 路径或
NAS 凭据。

## 10. 分项回滚与数据恢复边界

四类发布应能够独立回滚。执行回滚前先停止写流量和相关 Worker，保存故障现场、数据库与 NAS 状态；
不得为了让旧代码启动而盲目降级版本号。

### 10.1 数据库迁移

1. 若 migration 尚未提交且事务仍有效，回滚事务并确认 revision 与数据未改变。
2. 若已提交且 revision 明确提供**无损、已演练**的 downgrade，可执行
   `alembic downgrade <升级前版本>`，随后运行约束和旧版应用兼容验证。
3. downgrade 会丢字段/数据、无法恢复时间精度或只回退版本号时，不执行逻辑降级；停止写入，恢复升级前
   备份到新实例，核对备份时间点/WAL、行数和关键业务摘要后切换连接。
4. 数据恢复边界是最后一次已验证备份（或配置的 PITR/WAL 时间点）。该时间点之后的数据库写入不会由
   应用回滚自动找回，必须单独导出、审计并按业务批准合并。数据库恢复也不会恢复 Redis 会话或 NAS 文件。

### 10.2 前端发布

1. 保留上一版不可变静态目录和摘要；将 Nginx 的版本指针原子切回，执行 `nginx -t && nginx -s reload`。
2. 清理/失效本次 HTML 与 Service Worker 缓存（如有），静态 hash 资源可继续长期缓存；重新验证深层路由。
3. 前端回滚只恢复浏览器代码，**不回滚数据库、Redis、后端或 NAS**。只有旧前端与当前 API/传输协议向后
   兼容时才允许单独回滚，否则应按兼容矩阵联动回滚后端。

### 10.3 后端发布

1. 停止新版本继续接流和产生写入；待请求排空后，将流量切回上一版镜像 digest/制品和上一版配置。
2. 保持唯一 Application Leader 与调度互斥，逐实例验证数据库/Redis后再放量；不要同时运行协议或 schema
   不兼容的版本。
3. 后端制品回滚不撤销已提交事务、Redis 会话/缓存、Outbox 状态和 NAS 文件。若新版本已写入旧版不认识的
   schema 或状态，必须先执行经批准的数据修复/数据库恢复；不得直接启动旧代码碰运气。

### 10.4 NAS Worker 发布

1. 先停止领取新任务，等待当前租约内 I/O 完成；无法完成时终止新 Worker，并保留原 operation/submission，
   等租约过期后用**新唯一 ID**启动上一版 Worker 接管。
2. 对账数据库的 `sg_storage_operation`/submission 状态、目标摘要和 `.sgtmp-*.part`；同摘要正式文件按幂等
   结果处理，异摘要冲突禁止覆盖，临时文件只有在确认无活动租约且精确归属后才能清理。
3. Worker 回滚只更换消费者代码，不会撤销已经原子发布的 NAS 文件，也不会恢复已删除/覆盖的外部文件。
   数据库正式提交失败但 NAS 已发布时，应重试原 submission，不重新分配版本号/文件名。NAS 数据恢复边界
   取决于 NAS 快照/备份策略；数据库备份不能恢复 NAS 内容，NAS 快照也不能独自恢复数据库引用一致性。

## 11. 发布验收记录表

每次发布复制并填写下表，记录 commit、环境、开始/结束时间、执行人、退出码、结果（通过/失败/未执行）、
脱敏证据位置和失败单号。表内命令是仓库基线；若实际命令不同，必须写实际命令，不得预填“通过”。
构建成功、源码存在或 Mock 通过不能代替数据库集成、浏览器 E2E 或真实 SMB/NAS 结果。

## 12. 发布后最小业务冒烟

所有组件切换完成后，用专用验收账号和专用测试项目按顺序执行，并记录请求 ID、业务 ID、HTTP 状态、
数据库/Redis/NAS 的脱敏证据以及清理结果：

1. **登录与会话**：通过页面登录并调用 `/getInfo`；确认 Redis 创建会话，刷新页面后会话仍有效，退出后
   Token 失效。不得在证据中保存 Token。
2. **项目查询**：打开 Shot Grid 项目列表与一个有权限的项目详情，同时用无权限账号确认后端拒绝越权。
3. **数据库写入**：创建可安全清理的业务记录或执行批准的项目修改，确认事务落库、审计字段和
   `lockVersion` 正确，再通过正常业务动作清理；只执行 `SELECT 1` 不算业务写入验证。
4. **Redis 会话**：确认该登录会话由目标 Redis 逻辑库承载，并验证 logout/过期清理，不以单独 `PING`
   代替会话链路。
5. **创建存储操作**：为专用项目触发 NAS 初始化/对账，确认 Outbox 被唯一 Worker 领取并成功结算，固定
   目录存在且重复执行幂等。
6. **受保护文件下载**：上传/选择专用小文件并建立业务引用，通过鉴权下载校验摘要；未登录及无权限账号
   必须被拒绝，且不能通过 `/profile` 绕过。
7. **深层路由刷新**：分别直接访问并刷新 `/admin/<deep-route>` 与
   `/shot-grid/<deep-route>`，页面归属、静态资源和 API 前缀正确，无 404、串站或回退到另一 SPA。

冒烟失败立即停止放量并按第 10 节选择对应回滚，不要通过手工修改生产数据库或 NAS 文件掩盖失败。
冒烟是发布后的最小检查，不等于第 11 节完整验收矩阵。

## 13. 存活检查不等于业务验收

后端健康端点成功、进程/容器为 running、Nginx 返回 200、Swagger/ReDoc/OpenAPI 可访问，只能记录为
**服务存活/路由可达**。它们没有证明登录权限、PostgreSQL 写入、Redis 会话、防重放、文件授权、
NAS 原子发布、前端深层路由或业务 CRUD 正确，禁止据此把数据库集成、浏览器 E2E、SMB/NAS 或整体
业务验收标记为“通过”。只有第 11 节对应命令和第 12 节业务证据均按实际结果记录后，才能形成各自范围内
的验收结论。
