# Shot Grid 若依基座分析与实施方案

## 1. 文档状态

| 项目 | 内容 |
| --- | --- |
| 版本 | v1.7 |
| 状态 | 已完成基座分析、第一批普通管理/导入及默认关闭的 NAS 目录 Worker 后端交付；独立业务前端、真实 UNC 验收与完整生产闭环尚未实现 |
| 最近修订 | 2026-08-10 |
| 当前数据库 | PostgreSQL |
| 业务前端 | `shot-grid-frontend` 独立 Vue 3 应用 |
| 管理后台 | `ruoyi-fastapi-frontend` |
| 后端 | `ruoyi-fastapi-backend` |

本文回答两个问题：

1. 现有若依工程哪些能力可以直接复用，哪些只能参考，哪些必须新增；
2. 如何按“创建项目 → 导入镜头 Excel → 导入资产 Excel → 自动匹配 → 分配任务 → 版本审核”的顺序实施。

本文同时记录实施路线与当前交付边界。当前已实现 Shot Grid 数据库骨架、项目/成员/集/场次/镜头/资产/制作分项普通管理、镜头和资产 Excel 的安全预检与事务化提交，以及 NAS 目录 Outbox Worker、目录操作诊断和人工重试；Worker 在所有环境样例中默认关闭，真实 Windows Worker 账号、NAS/AD/共享 ACL 和隔离 UNC E2E 仍未完成。独立任务动作、资产需求人工处理、业务前端、版本文件发布、审核和完整 E2E 也仍未完成，不能由本文中的后续设计推断为已交付。

## 2. 结论

现有若依基座适合承载 Shot Grid，但不能只依靠代码生成器完成业务。建议采用以下边界：

- 直接复用登录、用户、角色、菜单授权、字典、Redis、日志、统一请求协议和受保护文件能力；
- 使用系统代码生成器辅助生成普通 CRUD 骨架，不让生成器决定数据库结构、状态机、项目权限、Excel 导入事务、NAS Outbox 或版本审核流程；
- 继续用若依管理后台维护用户、角色、字典、Shot Grid 菜单和 NAS 根目录等平台配置；
- `shot-grid-frontend` 保持独立业务应用，只显示 Shot Grid 菜单，不加载管理后台全部 `/getRouters` 结果；
- 新建 `module_shot_grid` 后端模块，遵循 Controller → Service → DAO → DO/VO 分层；
- PostgreSQL 表结构以 Alembic migration 为主，同时维护 SQLAlchemy DO 和 `sql/ruoyi-fastapi-pg.sql`；
- 为镜头和资产分别建设“模板下载 → 上传预检查 → 行级修正 → 幂等提交”的专用导入链路；
- 镜头表允许先引用尚未建立的资产名称，提交后形成“待匹配资产需求”；资产表后导入时按类型和规范化名称自动匹配，冲突项留给人工处理；
- 集数、场次数、镜头数和资产数由正式提交后的去重实体统计，不以 Excel 行数或前端计算结果为准。
- 镜头视频业务文件名固定为 `{项目代号}_EP{集号至少3位}_{场次号至少3位}_S{镜头号至少3位}_{制作人缩写}_V{版本号至少3位}_{服务端毫秒时间戳}.{mp4|mov}`，例如 `WGZR_EP001_001_S001_YJF_V001_1786094626499.mp4`。文件名版本号与平台版本及审核历史使用同一服务端值。
- NAS 目录 Worker 只由 Application Leader 的内部任务驱动，领取和结果回写使用短事务，SMB I/O 在线程中事务外执行；项目初始化目标相对 NAS 根目录，集/镜头/资产目标相对项目根目录。

## 3. 已由现有代码确认的基座能力

### 3.1 总体运行链路

```text
shot-grid-frontend
  → 复用 /login、/getInfo、Token 和传输加密协议
  → 调用 /shot-grid/** 业务 API
  → FastAPI Controller
  → Shot Grid Service（业务规则、状态机、事务）
  → DAO / SQLAlchemy Async
  → PostgreSQL

Redis
  → 登录会话、权限相关缓存、字典缓存、导入预览 Token、幂等和 Worker 协调

NAS
  → 由持久化 Outbox/Worker 执行目录创建和文件发布
  → 不在长数据库事务内直接执行 SMB I/O
```

### 3.2 能力复用矩阵

| 若依能力 | 当前代码事实 | Shot Grid 用法 | 结论 |
| --- | --- | --- | --- |

## 4. 代码生成器使用方案

### 4.1 可以使用的部分

代码生成器可以在正式 migration 建表后读取数据库元数据，生成：

- DO、DAO、Service、Controller 和 VO 初始骨架；
- 普通列表、详情、新增、修改、归档前的基础 CRUD；
- API 请求文件；
- 管理后台菜单和按钮权限 SQL 草稿；
- 简单管理页面草稿。

优先用于低耦合管理对象，例如 NAS 根目录配置、部分只读查询或简单辅助表。

### 4.2 禁止让生成器决定的内容

- 不通过 `/tool/gen/createTable` 建立正式业务表；
- 不用 `Base.metadata.create_all()` 替代 migration；
- 不直接采用生成 Service 的单表提交逻辑实现跨表事务；
- 不让生成 CRUD 更新任务、版本、审核、导入或存储状态；
- 不用生成的部门数据范围代替项目成员权限；
- 不把生成的管理端 Vue 页面直接当作 `shot-grid-frontend` 页面；
- 不用生成器处理 NAS 路径、Outbox、SHA-256、文件引用或补偿；
- 不用普通删除接口物理删除有历史版本、审核或文件引用的数据。

### 4.3 推荐步骤

```text
先冻结契约
→ 编写 PostgreSQL Alembic migration
→ 同步 DO 和 PostgreSQL 初始化 SQL
→ 执行 migration 建表
→ 将表导入代码生成器
→ 生成到临时目录
→ 人工提取 CRUD 骨架
→ 补齐项目权限、状态机、事务和测试
```

生成结果是脚手架，不是验收证据。

## 5. 菜单与独立业务应用方案

### 5.1 菜单结构

在 `sys_menu` 中建立稳定目录节点 `Shot Grid`，其 `route_name` 固定为 `ShotGrid`，下设六个业务菜单：

| 顺序 | 菜单名称 | 业务路由 | 路由键 | 页面职责 |
| --- | --- | --- | --- | --- |
| 1 | 工作台 | `/workbench` | `workbench` | 我的任务、待审核、修改中、近期截止 |
| 2 | 项目 | `/projects` | `projects` | 项目列表、创建、概览、成员与集场次 |
| 3 | 镜头管理 | `/shots` | `shots` | 镜头筛选、三种视图、导入和详情 |
| 4 | 资产库管理 | `/assets` | `assets` | 三类资产、导入、匹配和任务信息 |
| 5 | 版本审核 | `/reviews` | `reviews` | 待审核版本、审核单、批注和历史 |
| 6 | 文件与NAS | `/files` | `files` | 业务文件、NAS 路径、发布状态和故障 |

项目详情、镜头详情、资产详情、任务详情和版本审核页属于深层路由，不增加一级菜单。

### 5.2 为什么不能直接使用 `/getRouters`

当前 `/getRouters` 会从用户全部平台菜单生成路由树，`sys_menu` 也没有应用标识字段。管理后台通过自己的 `views/**/*.vue` 动态加载 `component`；独立的 `shot-grid-frontend` 不具备这些管理端组件。

如果业务端直接加载全部结果，会同时产生：

- 业务端尝试加载不存在的系统管理组件；
- Shot Grid 导航混入用户、角色、字典、监控等管理菜单；
- 菜单路径和组件字符串成为未经约束的运行时输入；
- 多应用菜单隔离和验收边界不清晰。

### 5.3 推荐实现

新增：

```http
GET /shot-grid/navigation
```

后端按当前用户的 `sys_role_menu` 权限，只查询 `route_name='ShotGrid'` 根节点的可见、启用后代，并返回白名单路由键。业务端维护静态路由注册表：

```text
workbench → WorkbenchPage
projects  → ProjectListPage
shots     → ShotManagementPage
assets    → AssetLibraryPage
reviews   → VersionReviewPage
files     → FileNasPage
```

菜单管理负责名称、图标、顺序、显示、停用和角色授权；它不能向业务端注入任意组件路径。MVP 不修改公共 `sys_menu` 增加 `app_code`，避免扩大平台表和 MySQL 兼容影响。未来出现多个独立业务应用时，再评审通用应用范围字段。

### 5.4 菜单种子交付

菜单与权限必须同时写入：

1. PostgreSQL Alembic 数据迁移；
2. `ruoyi-fastapi-backend/sql/ruoyi-fastapi-pg.sql`；
3. 可重复执行的幂等种子逻辑或 SQL；
4. 角色授权验收用例。

种子通过稳定 `route_name`、`path` 和 `perms` 查找，不依赖各环境完全相同的自增菜单 ID。

## 6. 字典使用方案

### 6.1 建议建立的字典

| 字典类型 | MVP 值 | 用途 |
| --- | --- | --- |
| `sg_project_type` | `ai_short_film` | 项目类型 |
| `sg_aspect_ratio` | `16:9`、`21:9`、`2.39:1`、`9:16`、`1:1` | 画幅 |
| `sg_asset_type` | `Character`、`Environment`、`Prop` | 资产类型 |
| `sg_project_phase` | `planning`、`asset_production`、`shot_production`、`review`、`delivery`、`completed` | 项目当前阶段 |
| `sg_task_priority` | `low`、`normal`、`high`、`urgent` | 任务优先级 |
| `sg_shot_size` | 评审后冻结 | 景别选择和显示 |
| `sg_camera_movement` | 评审后冻结 | 镜头运动选择和显示 |

### 6.2 字典边界

- 字典值使用稳定代码，中文只作为显示名称；
- 资产类型当前只接受三种值。“根据资产表决定有多少类型”表示统计本次文件实际包含了三种允许类型中的哪些类型，不表示上传文件可创建新的类型代码；
- 任务、版本、提交、审核和存储状态由代码状态机与数据库 `CHECK` 约束控制；
- 可以为这些状态建立只读展示字典，但管理员不能通过新增字典值扩展后端状态机；
- 改动资产类型、项目类型或状态代码必须同时评审数据库约束、API 校验、目录规则、文件命名和前端展示。

## 7. Excel 导入总体设计

### 7.1 业务顺序

```text
创建项目并完成 NAS 初始化
→ 下载镜头模板
→ 导入镜头 Excel
→ 根据去重键创建集、场次、镜头
→ 暂存镜头中引用的资产名称为待匹配需求
→ 下载资产模板
→ 导入资产 Excel
→ 创建三类资产、逐行制作分项和可选任务
→ 自动匹配镜头资产需求
→ 人工处理未匹配或冲突项
→ 项目进入任务分配和制作
```

这条顺序允许镜头表先出现“校园”“张三”“灯”等资产名称，同时避免拼写错误直接隐式创建正式资产。

### 7.2 统一四阶段协议

镜头和资产导入都使用：

```text
模板下载
→ preview：解析、规范化、校验、返回逐行结果
→ 用户修正文件或选择有效行
→ commit：重新校验、全事务提交、记录批次
```

禁止浏览器逐行调用新增接口。禁止预览成功后不重新检查数据库冲突。禁止把部分写入描述为导入成功。

### 7.3 导入批次

新增 `sg_import_batch`，至少保存：

- 项目、导入类型 `shot|asset`；
- 原文件名、SHA-256、模板版本；
- `previewed|committing|committed|failed|expired` 状态；
- 总行数、有效行、警告行、错误行和提交行数；
- 预览用户、提交用户、创建时间、提交时间；
- 客户端幂等键和净化后的失败摘要。

规范化行数据和逐行错误可以在 Redis 中按短 TTL 保存；正式提交结果和批次摘要进入 PostgreSQL。若监管要求保留原始 Excel，再通过平台受保护文件和 `sys_file_reference` 保存，不直接把临时文件路径写入业务表。

### 7.4 导入状态机

```text
previewed ──确认提交──→ committing ──事务成功──→ committed
    │                         └─失败──────────→ failed
    └─TTL 到期且未提交──────────────────────→ expired
```

- `committed` 批次不可再次消费；
- 相同用户、项目和幂等键重试返回原结果；
- `failed` 不得留下半成功业务数据；
- Excel 解析错误、数据库冲突和无权限使用稳定错误键返回。

## 8. 镜头 Excel 导入设计

### 8.1 关键字段和去重键

当前正式样表 `docs/镜头-样表.xlsx` 的解析契约：

```text
每个可见 Sheet = 一集，Sheet 名为 EP001、EP002……
A:P = 场次、镜头号、时长(s)、制作人、镜头缩略图、制作内容描述、景别、
      机位、镜头运动、焦段(mm)、场景、台词/对白、音效、色调参考、备注、镜头状态
```

- 只读取从 A1 开始的首段连续表头，Q:R 空白分隔后的 S:AK 辅助区不参与导入；
- 集号从 Sheet 名派生，成片顺序从 Sheet 内有效数据行顺序派生；
- “镜头缩略图”和“镜头状态”为只读列，整表忽略；
- “序”映射为 `scene_no=0`、`scene_code=000`；正片场次从 1 开始；
- 焦段按文本保留，不能用数值列读取后丢失 `35/25`、`24/18` 等值；
- 当前样表不包含角色和道具列，不允许从自然语言字段推断这两类资产。

规范键：

- 集：`(project_id, episode_no)`；
- 场次：`(episode_id, scene_no)`；
- 镜头：`(episode_id, shot_no)`；
- 成片顺序：按 Sheet 内有效行顺序稳定生成，不要求 Excel 提供序号列。

名称冲突不能静默覆盖。例如同一个 `episode_no` 在两行出现不同集名称时，预览返回错误。

### 8.2 数量计算

```text
总集数   = distinct(valid_sheet_episode_no)
总场次数 = distinct(episode_no, scene_no)
总镜头数 = distinct(episode_no, shot_no)
```

预览显示“文件内将新增、将复用、冲突”三组数量；项目概览最终以数据库有效实体重新聚合，不能直接保存 Excel 汇总数字。

### 8.3 资产名称处理

新增 `sg_shot_asset_requirement`：

| 字段 | 说明 |
| --- | --- |
| `project_id`、`shot_id` | 所属项目和镜头 |
| `asset_type` | 当前镜头样表只产生 `Environment`；模型保留 `Character`、`Prop` 供资产导入和人工关联 |
| `raw_name` | Excel 原始名称，用于审计和回显 |
| `normalized_name` | 去首尾空格、统一全半角及大小写后的匹配键 |
| `resolution_status` | `pending|matched|conflict|ignored` |
| `asset_id` | 匹配成功后的资产，可空 |
| `source_import_batch_id` | 来源镜头导入批次 |
| 审计字段 | 创建、更新和人工处理人 |

规则：

- 镜头导入不因场景资产尚未建立而失败；
- 同一镜头、类型、规范化名称只保留一条需求；
- 已存在唯一同名同类型资产时，可在镜头提交事务中直接匹配并建立 `sg_shot_asset`；
- 不存在时记为 `pending`；
- 多个候选或规范化冲突记为 `conflict`；
- 导入过程中不隐式创建正式资产。

### 8.4 镜头导入提交事务

一个提交事务包含：

- 导入批次状态；
- 集、场次和镜头；
- 集与镜头稳定目录快照及 NAS Outbox；
- 已匹配的 `sg_shot_asset`；
- 未匹配的 `sg_shot_asset_requirement`；
- 有制作人时创建或分配唯一镜头视频任务；
- 操作审计。

NAS 目录创建由事务提交后的 Worker 执行。

## 9. 资产 Excel 导入设计

### 9.1 模板字段

当前正式样表为 `docs/资产-样表.xlsx`，只解析 `Sheet1!A:G`：类型、名称、描述、制作分项、备注、状态、制作人。H:I 表头为空，不参与导入；“状态”为只读列。类型、名称、描述使用合并单元格表达父子关系，解析器只在实际合并区域内继承左上角值，不能对普通空白单元格全表前向填充。

当前样表验证结果为 20 个制作分项行、12 个逻辑资产，其中 Environment 2 个资产/4 个分项、Prop 4 个资产/4 个分项、Character 6 个资产/12 个分项；第 6—8 行缺少制作分项，只产生警告；第 16 行 `蒋浩/春霞` 因无法确定唯一主制作人而产生错误。

| 中文表头 | 标准字段 | 必填 | 规则 |
| --- | --- | --- | --- |
| 类型 | `assetType` | 是 | 只允许三种资产类型或对应中文别名 |
| 名称 | `assetName` | 是 | 项目内同类型规范化名称唯一 |
| 制作分项 | `productionItem` | 否 | 缺失只警告，保存到 `sg_asset_item`，版本提交前必须补齐 |
| 描述 | `itemDescription` | 否 | 保存到制作分项；合并单元格范围内继承左上角值 |
| 任务描述 | `taskDescription` | 否 | 当前样表无此列；未来模板提供时写入分项唯一任务 |
| 备注 | `remark` | 否 | 业务备注 |
| 制作人 | `assigneeUserName` | 否 | 必须是有效项目成员且缩写已设置 |

状态、缩略图、最新版本和完成度属于只读聚合字段，不允许通过 Excel 写入。

### 9.2 预检查和统计

- 将“角色、场景、道具”规范化为 `Character`、`Environment`、`Prop`；
- 统计文件包含的实际类型及各类型有效资产数；
- 合并区域内相同 `(assetType, normalizedName)` 只创建一个资产，每个明细行创建一个制作分项；
- 同一资产内非空制作分项重复时返回行错误；制作分项为空只返回警告，允许导入后补充，版本提交前强制校验；
- 制作人每行只能解析出一名主制作人，复合制作人值返回错误；
- 数据库已存在的同名同类型资产可以作为父资产复用并新增分项，但不得静默覆盖资产字段；字段冲突返回错误；
- 如需支持更新已有字段，后续单独增加显式 `update_existing` 模式和字段级变更预览；MVP 只新增资产或制作分项；
- 制作人匹配规则与镜头导入一致；
- 预览展示导入后预计可自动解决的镜头资产需求数量。

### 9.3 自动匹配

资产提交后，在同一数据库事务中按以下键处理：

```text
(project_id, asset_type, normalized_name)
```

- 唯一匹配：创建幂等 `sg_shot_asset`，需求改为 `matched`；
- 无匹配：保持 `pending`；
- 多候选或历史脏数据：改为 `conflict`，禁止自动选择；
- 人工解决必须使用专用动作接口，记录操作者和原始名称；
- 资产改名不能自动重写已经审计的 `raw_name`，应重新运行匹配并保留历史。

### 9.4 资产导入提交事务

一个提交事务包含：

- 导入批次状态；
- 去重资产、逐行 `sg_asset_item` 及资产目录 Outbox；
- 制作分项有单一主制作人时创建或分配该分项唯一资产图片任务；
- 待匹配需求解析和 `sg_shot_asset` 关系；
- 操作审计。

资产表提交成功不代表 NAS 目录已经创建成功；前端必须分别展示业务提交状态和目录状态。


```http

POST /shot-grid/projects/{projectId}/asset-requirements/{requirementId}/ignore
POST /shot-grid/projects/{projectId}/asset-requirements/rematch
```

预览和提交都必须校验：登录、平台权限、项目成员、项目角色、项目归属、项目存储 `ready`、文件限制和幂等键。

### 10.4 已实现的目录诊断与人工重试

```http
GET  /shot-grid/projects/{projectId}/storage
GET  /shot-grid/projects/{projectId}/storage/operations
GET  /shot-grid/projects/{projectId}/storage/operations/{operationId}
POST /shot-grid/projects/{projectId}/storage/retry
POST /shot-grid/storage-operations/{operationId}/retry
```

- 操作列表和详情仅对项目总监或具有全项目范围且拥有接口权限的管理员开放，并裁剪租约、内部幂等键、凭据和绝对路径；分页 `keyword` 只匹配相对路径、稳定错误键和净化错误摘要，默认按 `createTime` 倒序、`operationId` 倒序稳定排序。
- 项目重试要求项目存储为 `failed`，请求携带 `lockVersion`、非空原因和 `X-Idempotency-Key`；动态重试只允许最终失败的集、镜头或资产目录，且必须重新校验项目、业务对象和路径快照。
- 人工重试保留失败操作并新建 `reconcile_directory`，与原因及操作日志同一事务，返回真实 HTTP 202。项目级受理后存储回到 `initializing`；动态目录失败和重试不降级已就绪的项目根存储。
- 制作人员可读取 `ready` 项目路径；非 `ready` 时完整 UNC 只向项目总监或管理员返回。

## 15. 验收门禁

### 15.1 镜头导入

- 文件内重复键、跨文件重复键和名称冲突能定位到行与字段；
- 多 Sheet 能按 `EP001` 等名称正确创建集，非法或重复集 Sheet 在预览阶段失败；
- “序”稳定映射为场次 `000`，且同集镜头号跨场次不能重复；
- 解析范围只覆盖 A:P，辅助区不产生伪镜头；组合焦段按文本无损保留；
- 提交后集、场次和镜头数量等于去重实体数量；
- 任一选中行失败时本批次无半成功数据；
- 相同幂等键不会重复创建实体、任务或目录操作；
- 未建立资产产生待匹配需求，不产生正式资产；
- 非项目总监或无导入权限用户被后端拒绝。

### 15.2 资产导入和匹配

- 只允许三种资产类型；
- 同类型规范化名称唯一；
- 自动匹配只处理唯一候选；
- 冲突不被静默选择；
- 手工解决有审计并且重复请求幂等；
- 项目概览的总资产数与有效数据库实体一致。
- 项目概览同时提供制作分项总数和完成数，整体进度按镜头与制作分项计算。

### 15.3 菜单和权限

- Shot Grid 业务端只收到六个一级业务菜单；
- 角色取消某菜单授权后，导航和对应接口都不可用；
- 知道 URL 不能绕过接口权限或项目成员权限；
- 管理端系统菜单不会被业务端解析。

### 15.5 NAS 目录 Worker

- 所有环境样例默认 `SHOT_GRID_STORAGE_WORKER_ENABLED=false`；非 PostgreSQL、非 Application Leader 或开关未启用时不注册/不消费内部任务。
- 每次领取前检查 Leader，数据库使用 `FOR UPDATE SKIP LOCKED`；终态回写必须同时匹配 operation、owner 和 attempt，租约过期后新 Worker 可接管，旧 Worker 不能覆盖新结果。
- 领取事务在 NAS I/O 前提交；建目录、路径解析和写探针在线程中完成；成功、重试等待或最终失败在新短事务写回。
- `initialize_project` 与项目级 `reconcile_directory` 相对 NAS 根目录；集、镜头和资产操作相对项目根目录。所有路径拒绝越界、非法片段、符号链接、Windows reparse point 和普通文件占位。
- 项目初始化成功后才为 `ready`，项目级最终失败才为 `failed`；动态目录失败不把项目根存储降级为失败。
- 人工重试要求项目总监/管理员、平台接口权限、非空原因和幂等键；保留原失败操作并新建 `reconcile_directory`，操作列表不暴露租约、幂等键、凭据或服务器绝对路径。
- 默认重试为最多 5 次和 `5/15/60/300` 秒退避。软超时只做诊断并继续续租，不硬杀仍执行的 SMB 线程；当前批内串行，尚未提供批内并发配置。
- 自动化文件系统用例只可显式开启本地测试根目录；正式启用前必须使用真实 Windows 服务账号、隔离 UNC 根目录和 NAS/AD/共享 ACL 覆盖成功、不可达、不可写、路径冲突、失锁接管及人工重试。

## 16. 主要风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 直接用代码生成器完成核心业务 | 限定为骨架，状态机和跨表事务人工实现并测试 |
| 业务端加载全部若依菜单 | 使用 Shot Grid 范围导航和静态路由白名单 |
| 镜头表先导入但资产不存在 | 持久化待匹配需求，资产后导入自动解析 |
| Excel 直接落库出现半成功 | preview/commit、全事务、批次和幂等 |
| 工作簿重新保存后文件摘要变化，未命名资产分项可能失去跨文件稳定身份 | `import_row_key` 只保证同一字节文件幂等；长期跨文件幂等需模板稳定 `rowUid` 或人工治理，不能声称当前已覆盖 |
| 资产拼写差异造成重复 | 保存原名和规范名，只对唯一候选自动匹配 |
| 字典新增值但后端不认识 | 状态机代码与 `CHECK` 是权威，字典只负责展示或受控选项 |
| NAS I/O 阻塞数据库事务 | 持久化 Outbox、Worker、租约、重试和对账 |
| Worker 源码或临时目录测试被误当作 NAS 上线证据 | 所有环境默认关闭；正式 Windows 服务账号、隔离 UNC 根目录和共享 ACL E2E 通过后再显式启用 |
| 软超时被误当作能中止 SMB 线程 | 超时只记诊断并继续心跳；等待物理 I/O 退出，不释放租约后让旧线程后台写入 |
| 独立前端复制管理后台 | 管理能力留在后台，业务端只实现制作流程 |
| 菜单种子依赖固定 ID | 使用稳定 routeName/path/perms 做幂等查找 |
| 只验证成功路径 | 覆盖回滚、幂等、并发、越权、NAS 失败和刷新恢复 |

## 17. 后续仍需确认的参数

当前样表的模板版本、`.xlsx` 限制、文件/ZIP/解压/OOXML 复杂度/单格与总文本/预览 JSON 安全阈值、预览 TTL、资产名称规范化和分隔符规则已经由配置与实现冻结。全部 OOXML Sheet（含隐藏 Sheet）在 `openpyxl` 前流式预检，预览载荷在 Redis 写入和数据库提交前检查。以下内容不会改变总体架构，但必须在对应后续阶段确认：

1. 是否有超出两份正式样表的真实历史工作簿，需要补充兼容规则；
2. 当前正式模板只承诺 `.xlsx`；如确有历史 `.xls` 需求，需另行提供样本并评审；
3. 除已确认的 Sheet 集代码 `EPnnn`、场次“序”和镜头代码 `Snnn` 外，是否还需兼容其他字母编号；
4. 当前上传原文件只做临时解析；如需长期保留，需冻结受保护文件引用和保留期限；
5. 管理员、项目总监和制作人员的初始平台角色种子；
6. NAS Worker 的正式 Windows 服务账号、共享 ACL、隔离测试根目录和生产启用审批；自动退避策略已默认冻结为最多 5 次及 `5/15/60/300` 秒，可由部署配置收紧；
7. 未命名资产制作分项的长期稳定 `rowUid` 方案，或重存工作簿后的人工去重治理流程。

这些参数未冻结时可以建设基座和测试框架，但不能声称导入契约已经生产就绪。
