## 2. 产品目标与系统边界

### 2.1 产品目标

系统用于管理 AI 影视短片从项目建立到镜头、资产制作与审核完成的协作过程，重点解决：

1. 项目管理人统一建立项目、集、场次、镜头和资产；
2. 将镜头视频任务和资产图片任务分配给制作人员；
3. 制作人员在线下制作，在平台上传产出物；
4. 每次上传形成不可覆盖的版本和对应审核单；
5. 项目管理人或管理员基于具体版本提出结构化修改问题，制作人随下一版本逐条说明处理方式，审核人在新版本逐条确认后退回或确认最终版；
6. 所有成员通过项目权限访问同一套业务数据和 NAS 项目目录；
7. 项目概览提供统一、可追溯的进度统计；
8. 镜头或资产详情使用一条可展开的生产履历链，直观呈现来源、委派、制作、版本、审核、修改和定版结果，并可进入对应任务、版本或审核详情。

### 2.2 核心业务主线

```text
项目
├── 集
│   └── 场次
│       └── 镜头（创建或导入后默认为未分配）
│           └── 委派后创建的唯一镜头视频任务
│               └── 版本 V001...Vnnn
│                   └── 每版本一个自动审核单
└── 资产（角色/场景/道具）
    └── 制作分项（一个或多个，创建或导入后默认为未分配）
        └── 委派后创建的唯一资产图片任务
            └── 版本 V001...Vnnn
                └── 每版本一个自动审核单
```

### 2.3 平台负责

- 项目、项目成员及项目内角色管理；
- 集、场次、镜头、资产的创建、导入、查询和维护；
- 任务分配、改派、状态跟踪和个人工作台；
- 镜头、资产制作分项及项目综合排期，包含人员泳道、任务甘特、首版基线、改期审计和人员撞期提示；
- 图片、视频产出物上传和版本管理；
- 自动审核单、跨版本修改问题、逐版本处理说明、逐条确认、审核动作和最终版本确认；
- NAS 项目目录初始化、路径登记、权限内展示和文件落位；
- 项目进度统计、审计和站内通知。

### 2.4 平台不负责

- 在线生成图片或视频；
- 在线剪辑、调色、混音或工程文件编辑；
- Premiere、达芬奇、After Effects 等桌面软件插件；
- 制作人员本地工程目录和中间素材管理；
- 工时、预算、成本结算、人员容量、任务依赖、关键路径和自动排期；
- 匿名外链、客户门户和外部审核；
- AI 自动拆本、自动审核或自动生成提示词。

## 3. 业务术语与层级

| 术语 | 英文/代码 | 定义 |
| --- | --- | --- |
| 项目 | Project | 一部 AI 影视短片的业务和权限边界 |
| 集 | Episode | 项目下的分集实体 |
| 场次 | Scene | 一集内的叙事场次 |
| 镜头 | Shot | 场次内可独立制作和审核的视频单元 |
| 资产 | Asset | 角色、场景或道具图片资产 |
| 任务 | Task | 分配给一名制作人员的镜头视频或资产图片制作工作 |
| 版本 | Version | 一次正式提交、不可覆盖的制作产出物记录 |
| 修改问题 | Review Issue | 审核人在某个来源版本上提出的结构化问题；现有协议兼容名称为 `Note` |
| 问题处理说明 | Issue Response | 制作人提交后续版本时，针对一条未关闭问题说明本版如何处理 |
| 问题确认 | Issue Verification | 审核人在后续版本上逐条确认历史问题已修复或仍然存在 |
| 审核动作 | Review Action | 通过、退回修改或稍后决定 |
| 审核单 | Review List | 按顺序组织待审核版本的业务对象 |
| 最终版 | Final Version | 经审核通过、作为任务最终结果的唯一版本 |

层级不变量：

- 一集必须且只能属于一个项目；
- 一个场次必须且只能属于一集；
- 一个镜头必须且只能属于一个场次；
- 一个资产必须且只能属于一个项目；
- 一个任务必须且只能属于一个镜头或一个资产制作分项；
- 一个版本必须且只能属于一个任务；
- 修改问题必须永久绑定首次提出它的来源版本；问题处理说明和问题确认同时绑定问题与本次新版本；
- 修改问题可以跨多个后续版本保持 open，但不得复制、迁移或改绑来源版本；
- open 问题还必须返回当前待处理归属版本；初始归属来源版本，每次审核确认 `still_present` 并退回时推进到当前被审核版本；来源版本只保留处理与确认历史，不再显示为当前待处理；
- 审核动作必须绑定当前被审核版本；
- 任何跨层级写操作都必须验证资源属于同一个项目。

## 4. 用户、角色与权限

### 4.1 身份来源

- 登录账号必须复用 RuoYi 平台用户，不另建业务账号体系。
- 平台管理员是全局授权能力，不作为 `sg_project_member` 中的项目角色。
- 项目管理人和制作人员是项目内角色；同一用户在不同项目可以拥有不同角色。制作人标识统一取平台用户昵称，不在项目成员关系中重复维护。
- 平台角色与项目角色仍是两层授权事实，不把 `sys_user_role` 当成项目成员关系；但项目创建以及成员新增/恢复、项目角色变更、成员移除必须通过 Shot Grid 专用服务按固定映射增量维护平台接口权限：`director -> shotgrid_admin`、`creator -> shotgrid_creator`。项目归档不触发该同步。

### 4.2 项目角色

| 代码 | 中文 | 业务职责 |
| --- | --- | --- |
| `director` | 项目管理人 | 项目管理、成员管理、任务分配、审核和最终版确认 |
| `creator` | 制作人员 | 查看本人任务、等待管理人员确认开工、查看退回问题、逐条填写处理说明并提交新版本 |

### 4.3 权限判断规则

访问项目资源必须同时满足：

```text
有效登录态
AND 平台接口权限
AND 项目成员身份或明确的全项目管理权限
AND 项目角色允许当前动作
AND 目标资源确实属于当前项目
```

前端按钮显隐只用于改善体验，不能替代后端鉴权。

固定平台角色包只提供接口能力，不提供项目数据范围；项目成员关系只提供项目范围和项目角色，也不提供接口能力。任何一层缺失都必须拒绝，禁止因已绑定 `shotgrid_admin` 或 `shotgrid_creator` 就跳过项目成员、资源归属、状态或 `allowedActions` 校验。

任务与版本页面必须执行平台权限和后端 `allowedActions` 的交集门禁；查看任务、开始/编辑任务、提交版本、查询当前提交、重试失败提交、查看版本历史/详情和下载文件是独立权限，不能互相推导。镜头任务仅允许具备 `shotgrid:task:start` 的项目 `director` 或 `has_all_scope` 管理人员确认开工；制作人只能等待，不能自行开始。管理人线下确认依赖资产齐备后提交 `{ lockVersion, shotLockVersion, assetsConfirmed: true }`，服务端在锁内复核管理范围、任务与镜头版本、状态及当前负责人仍为有效 `creator`，并在同一事务审计人工确认。资产任务同样由具备上述权限和范围的管理人员按制作分项确认，以 `{ lockVersion, assetLockVersion, assetItemLockVersion, startConfirmed: true }` 提交；锁内复核任务、父资产和分项三份版本、分项内容及有效负责人，同事务审计。只递增任务版本，不修改父资产和分项元数据版本；其他分项不随本分项或共享目录开工；版本 preflight/create 和失败提交重试仍只允许当前受派的活动制作人员本人，管理人不得代提交或代重试。后端仍必须按实时项目成员/角色、任务负责人、任务/项目状态、未解决提交和文件关系重新校验。

### 4.5 项目成员规则

- 创建项目时必须同时确定至少一名项目管理人；创建人可以是首位项目管理人。
- 一个项目始终至少保留一名活动项目管理人，不得移除或降级最后一名活动项目管理人。
- 项目成员采用可审计软移除；项目范围、成员列表和任务分配只认活动成员，历史任务仍保留原成员外键。
- 项目成员列表支持按项目内角色查询；传入 `director` 或 `creator` 时只返回该角色，不传角色时返回项目全部活动成员。
- 重新加入已移除用户时恢复原项目成员关系，不新建重复关系。
- 制作任务只能分配给当前项目中项目角色为 `creator` 的活动成员；项目管理人不能作为镜头或资产制作人进入委派下拉。Excel 导入不提供制作人选择。
- 可被分配任务的制作人员必须设置平台用户昵称，例如 `YJF`；Shot Grid 不再提供独立的制作人缩写字段。
- 任务委派和版本文件名生成统一使用平台用户昵称；同项目存在昵称重复时，委派候选项必须同时显示账号等可区分信息，不能仅凭昵称自动选择。
- 成员姓名变更不得改变已生成的历史文件名。
- 移除仍有未完成任务的成员前，必须先完成改派或显式取消处理，不能留下无负责人任务。

### 4.6 受管平台角色增量绑定

项目创建、成员新增或恢复、项目角色变更、成员移除由 Shot Grid 专用后端服务完成项目成员与平台角色的受控同步。独立业务前端只提交稳定的 `projectRole=director|creator`，不得提交平台 `roleId`、`roleKey`、菜单 ID，不得调用 `/system/user/authRole`、`/system/role/*` 或任何其他 `/system/*` 接口。

固定映射：

| 项目角色 | 受管平台角色键 | 用途 |
| --- | --- | --- |
| `director` | `shotgrid_admin` | Shot Grid 项目管理人所需的平台接口权限包，不等于平台超级管理员 |
| `creator` | `shotgrid_creator` | Shot Grid 制作人员所需的平台接口权限包 |

增量绑定必须遵守：

1. 新增或恢复活动成员时，若目标 `sys_user_role` 不存在，则在同一数据库事务内只新增映射所需的一条关系，并写入 `sg_managed_user_role` 来源标记；若该关系原已存在但没有来源标记，只复用且不得接管其所有权。
2. 项目角色变更在同一未提交事务内更新成员角色，再以更新后的全部活动成员关系同步映射；同步同一用户时先新增当前需要但不存在的映射，再判断是否可撤回旧映射，任一步失败全部回滚，对其他事务不存在可见权限空窗。
3. 成员移除后，必须按目标用户全部 `member_status='active'` 项目成员关系重新计算依赖；该查询不按项目状态过滤，因此归档项目也继续计入。只有旧映射已无任何活动成员依赖且存在 Shot Grid 来源标记时，才删除该一条 `sys_user_role`，来源标记由复合外键级联删除。项目归档不触发角色撤回。
4. 没有来源标记的平台角色、用户其他平台角色、手工分配角色和其他业务管理的角色一律不得删除；禁止通过全量替换用户角色实现同步。
5. 同一用户在多个项目中依赖同一映射角色时，只保留一条平台角色关系；退出最后一个依赖项目之前不得撤回。并发新增、改角和移除必须锁定相关项目/成员/受管绑定并依赖唯一约束避免重复或误撤权。

两个受管角色包都必须至少包含启用的 `shotgrid:navigation:list` 和一个启用的 Shot Grid 业务导航权限。两个角色包都禁止包含：

- 超级权限 `*:*:*`；
- 跨项目范围 `shotgrid:project:all`；
- 任何 `system:*` 权限；当前实现进一步拒绝全部非 `shotgrid:` 权限；
- NAS 存储根管理写权限 `shotgrid:storageRoot:add`、`shotgrid:storageRoot:edit`、`shotgrid:storageRoot:probe` 及后续等价写权限。

跨项目管理员和存储根管理员必须使用独立、非受管的平台角色。后端在角色选项查询及每次项目/成员写入时都要按 `roleKey` 重新校验固定角色存在、启用、未删除且权限包安全；配置漂移时失败关闭，不能回退到任意同名角色或由前端选择角色 ID。

角色选择只通过两条只读专用 API 获取：创建项目使用 `GET /shot-grid/project-role-options`，项目成员维护使用 `GET /shot-grid/projects/{projectId}/role-options`。响应固定投影 `projectRole/projectRoleLabel/systemRoleId/systemRoleKey/systemRoleName`；`systemRoleId` 和 `systemRoleKey` 只用于显示、诊断和映射完整性校验，写请求仍只提交 `projectRole`。

数据库提交成功后，项目创建以及成员新增/恢复、改角、移除控制器通过 `ApiGroup.USER_PERMISSION_MUTATION` 清理平台 `/getInfo`、`/getRouters`、用户/角色/菜单和数据范围相关缓存；项目创建只在业务响应码 202 时触发，成员写只在成功响应时触发，不得先清缓存再提交数据库。`/shot-grid/navigation` 当前不使用接口缓存，但目标用户已经打开的 SPA 仍持有旧 Pinia 身份/导航快照，必须刷新页面、重新执行 `/getInfo` 与 `/shot-grid/navigation` 初始化或重新登录；成功响应不承诺跨会话推送或自动刷新目标用户页面。

平台管理端修改角色键、菜单权限包或用户角色时必须经过同一安全保护；固定角色键不得改名/删除，启用角色不得提交不安全权限包，活动成员所需或带来源标记的关系不得由通用用户角色入口移除。存量成员在角色配置完成后，由同时拥有 `shotgrid:project:all` 和 `system:user:edit` 的管理员调用 `POST /shot-grid/platform-role-bindings/reconcile` 对账。

## 5. 项目需求

### 5.1 项目字段

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 项目名称 | 是 | 通常为中文，例如“罗刹夫人”；去除首尾空格，长度与非法字符限制由接口契约冻结 |
| 项目代号 | 是 | 2—12 位大写英文字母或数字，例如 `LCFR`；默认作为产出物文件名前缀 |
| 画幅 | 是 | 仅允许 `16:9`、`21:9`、`2.39:1`、`9:16`、`1:1` |
| 项目类型 | 是 | MVP 仅允许 `AI影视短片`，内部代码建议为 `ai_short_film`，必须保留可扩展字典设计 |
| 项目描述 | 否 | 项目背景、创作方向、交付目标等文本说明 |
| NAS 存储地址 | 是 | 从管理员配置并允许使用的 NAS 根目录中选择，创建前展示最终项目路径预览 |
| 项目管理人 | 是 | 至少一名有效平台用户 |
| 项目成员 | 否 | 可在创建时添加，也可创建后维护 |
| 当前阶段 | 是 | 默认“制作规划”，用于项目概览展示 |

补充规则：

- MVP 中“项目代号”和“产出物文件名前缀”是同一个业务值，统一保存为 `project_code`，不再保留可与其漂移的第二个 `file_prefix` 业务字段。
- 项目代号在有效、未归档项目范围内大小写不敏感唯一。
- 项目名称可以重复，但同一 NAS 父目录下的项目物理路径不得冲突。
- 项目描述不得包含可执行 HTML；展示时必须按普通文本或经过安全净化的格式处理。

### 5.2 项目状态与阶段

项目生命周期状态：

| 代码 | 中文 | 说明 |
| --- | --- | --- |
| `preparing` | 筹备中 | 项目已创建，正在建立成员、集、镜头和资产 |
| `active` | 进行中 | 存在已分配或正在制作、审核的任务 |
| `completed` | 已完成 | 所有纳入交付的镜头和资产制作分项均完成 |
| `archived` | 已归档 | 项目只读保留，不再参与日常工作台统计 |

“当前阶段”是面向业务展示的独立字段，依次展示为“制作规划、资产制作、镜头制作、版本审核、交付确认、项目完成”；内部代码固定为 `planning`、`asset_production`、`shot_production`、`review`、`delivery`、`completed`。阶段由项目管理人显式维护，不得通过修改阶段绕过任务和版本状态机。

### 5.3 创建项目流程

1. 用户填写并校验项目基本信息；
2. 用户选择 NAS 配置根目录，系统计算并展示最终项目目录；
3. 后端验证项目代号、成员、NAS 路径和写权限；
4. 后端检测同名目录、路径越界和并发创建冲突；
5. 在同一数据库事务中创建项目记录及至少一名项目管理人成员，并通过专用服务按固定映射增量绑定受管平台角色和来源标记；
6. 在 NAS 上创建项目初始目录；
7. 记录目录初始化结果和审计日志；
8. 全部成功后才向用户显示“项目创建成功”。

数据库与 NAS 文件系统无法形成真正的单一事务，因此实现必须采用可恢复的补偿流程：

- 只能删除本次操作新建且确认为空的目录，不能清理任何预先存在目录；
- 数据库失败时应补偿本次新建目录；补偿失败时记录告警和待处理状态；
- NAS 创建失败时不得把项目显示为可正常使用；
- 重试必须幂等，不得重复创建成员、目录或项目记录。

### 5.4 修改与归档

- 修改项目名称不得自动移动或重命名已投入使用的 NAS 项目根目录。
- 项目创建时应保存不可变的 NAS 项目路径快照；路径迁移必须作为独立的管理员操作设计、审核和审计。
- 画幅、类型或项目代号一旦已有版本文件，默认禁止直接修改；确需修改必须明确对历史文件名和目录的影响。
- 项目归档不等于删除；归档后历史版本、修改问题、逐版本处理说明与确认记录、审核动作和 NAS 文件均保留。
- `completed` 和 `archived` 项目中的集、场次、镜头、资产、资产制作分项以及两类 Excel 导入均只读；前端隐藏写入口不能替代后端在写事务中的状态复核。`completed` 项目仍可由有权限的项目管理人归档，`archived` 不再提供业务写动作。
- MVP 不提供从平台永久删除整个 NAS 项目目录的能力。

## 6. NAS 目录与存储规则

### 6.1 基本定义

NAS 地址是由后端服务器访问的 UNC 网络共享路径，例如：

```text
\\192.168.10.64\策划部
```

系统根据所选 NAS 根目录、项目类型目录名和项目路径名生成项目根目录：

```text
{NAS根目录}\{项目类型目录名}\{项目路径名}
```

示例：

```text
\\192.168.10.64\策划部\AI影视短片\罗刹夫人
```

浏览器不能被假定为能够直接访问或打开 UNC 路径。前端 MVP 必须提供“查看路径”和“复制路径”，只有部署环境已经安装并确认专用桌面协议处理器时，才可以增加“打开目录”。

### 6.2 NAS 配置边界

- 普通用户不能输入任意服务器路径，只能从管理员预先配置的 NAS 根目录中选择。
- 后端必须以服务账号访问 NAS；浏览器端不得获得 NAS 账号或密码。
- 后端必须对规范化后的最终路径进行允许根目录校验，防止 `..`、绝对路径替换、符号链接或重解析点逃逸。
- 日志不得记录 NAS 凭据；路径是否属于敏感信息由部署策略决定，接口只向有项目访问权的成员返回。
- 创建项目前必须验证根目录存在、可访问并具有所需创建/写入权限。

### 6.3 项目初始目录

创建项目时必须至少生成：

```text
{项目根目录}
├── ASSET
│   ├── Character
│   ├── Environment
│   └── Prop
└── VIDEO
```

完整路径示例：

```text
\\192.168.10.64\策划部\AI影视短片\罗刹夫人
\\192.168.10.64\策划部\AI影视短片\罗刹夫人\ASSET
\\192.168.10.64\策划部\AI影视短片\罗刹夫人\ASSET\Character
\\192.168.10.64\策划部\AI影视短片\罗刹夫人\ASSET\Environment
\\192.168.10.64\策划部\AI影视短片\罗刹夫人\ASSET\Prop
\\192.168.10.64\策划部\AI影视短片\罗刹夫人\VIDEO
```

### 6.4 动态目录

- 创建或导入新集时，在 `VIDEO` 下按集编号创建集目录。
- 创建或导入新镜头时只建立数据库对象，不立即创建镜头目录；管理人员在线下确认依赖资产齐备并点击“开始任务”后才冻结目录名并通过 Outbox 异步创建。
- 场次作为业务实体参与文件名和筛选，但按当前需求不单独创建物理目录。
- 稳定目录代码使用集目录 `EP01`、`EP02` 与镜头目录 `{sceneNo:03d}_{shotNo:04d}`，例如 `001_0001`。
- 目录编号必须由后端基于开始制作时冻结的场次号和场内镜序生成；数据库稳定主键 `shot_id` 与 NAS 路径无关，也不得使用 Excel 行号。

```text
{项目根目录}\VIDEO
├── EP01
│   ├── 001_0001
│   └── 001_0002
└── EP02
    ├── 001_0001
    └── 001_0002
```

镜头版本目标路径示例：

```text
\\192.168.10.64\策划部\AI影视短片\罗刹夫人\VIDEO\EP01\001_0001\LCFR_EP001_001_0001_YJF_V001_01.mp4
```

### 6.5 资产目录

资产类型与目录映射固定为：

| 资产类型 | 中文 | 目录 |
| --- | --- | --- |
| `Character` | 角色 | `ASSET\Character` |
| `Environment` | 场景 | `ASSET\Environment` |
| `Prop` | 道具 | `ASSET\Prop` |

推荐每个资产建立独立子目录，以避免同类型资产版本混杂：

```text
ASSET\Character\张三三视图
ASSET\Environment\校园图
ASSET\Prop\灯
```

资产版本目标路径推荐为：

```text
{项目根目录}\ASSET\{资产类型}\{资产目录名}\{业务文件名}
```

原始示例同时出现了“直接存入类型目录”和“每资产独立子目录”两种方式，最终实现前必须完成第 21 节 D-03 决策。

### 6.6 目录名安全规则

- 用户可编辑名称不能原样作为路径片段，必须先执行 Windows/SMB 兼容校验。
- 禁止 `\ / : * ? " < > |`、控制字符、`.`、`..`、末尾空格和末尾句点。
- 禁止 Windows 保留名称，例如 `CON`、`PRN`、`AUX`、`NUL`、`COM1`、`LPT1` 等。
- 路径片段净化后为空、重名或超长时必须阻止创建，并提示用户修改名称，不能静默生成不可识别目录。
- 任何目录创建、文件写入、移动和清理都必须再次校验最终解析路径仍位于项目根目录内。

### 6.7 NAS 文件落位成功语义

制作人员看到“版本提交成功”时，必须同时满足：

1. 平台已收到并校验上传文件；
2. 文件已经以正式业务文件名安全写入目标 NAS 目录；
3. 文件摘要或等价完整性校验通过；
4. 版本、版本文件引用和自动审核单已经持久化；
5. 任务已经进入待审核状态。

如果其中任一步失败，不得生成对用户可见的半成品版本，也不得显示“提交成功”。实现可以采用临时文件、原子重命名、补偿任务和对账机制，但必须保证重试幂等，并保留可诊断记录。

## 7. 集与场次需求

### 7.1 集

每集至少包含：集编号、集名称/标题、描述、排序、状态和审计信息。

- 集编号在项目内唯一，例如 `01`、`02`；展示可格式化为 `EP01`。
- 集编号创建后原则上不修改；修改会影响 NAS 目录和镜头业务文件名，必须走受控迁移。
- 归档集前必须检查其下场次、镜头和未完成任务。

### 7.2 场次

每个场次至少包含：所属集、场次编号、场次名称、场次描述、排序、状态和审计信息。

- 场次编号在一集内唯一，例如 `001`、`002`。
- 场次用于镜头组织、筛选和业务文件名，不按当前基线创建独立 NAS 目录。
- 删除采用归档或逻辑删除，不能级联删除已有镜头、版本或审核记录。

## 8. 镜头管理需求

### 8.1 镜头字段

镜头列表正式字段为：

| 字段 | 说明 |
| --- | --- |
| 集 | 所属父级集 |
| 场次 | 所属父级场次 |
| 本场第 N 镜 | 面向用户的连续序位；导入时按同场有效行顺序生成，拖拽时自动重排 |
| 镜序代码 | 与“本场第 N 镜”是同一事实；第 1 镜为 `0001`，第 2 镜为 `0002`，每个场次重新从 `0001` 开始 |
| 时长 | 统一按整数毫秒存储，页面可显示秒或时间码 |
| 制作人 | 从该镜头唯一任务聚合 |
| 镜头缩略图 | 从当前最新版本或最终版本的缩略图聚合 |
| 制作内容描述 | 对镜头画面和动作的制作要求 |
| 景别 | 例如远景、全景、中景、近景、特写 |
| 机位 | 相机高度、角度或位置说明 |
| 镜头运动 | 推、拉、摇、移、跟、升降等 |
| 焦段 | 以毫米为单位的数值或经确认的描述 |
| 场景 | 关联 `Environment` 资产，可多选 |
| 角色 | 关联 `Character` 资产，可多选 |
| 台词/对白 | 镜头内对白文本 |
| 音效 | 环境声、拟音或音效要求 |
| 色调参考 | 色彩、光线和氛围要求，可关联参考文件 |
| 备注 | 其他制作说明 |
| 当前最新反馈 | 从任务当前 open 修改问题聚合，只读 |
| 状态 | 根据唯一任务和版本状态聚合，只读 |

道具通过镜头与 `Prop` 资产关系保存，可以作为可选列和详情字段展示。

### 8.2 查询与筛选

镜头页必须支持：

- 按集筛选；
- 按场次筛选；
- 按镜头号精确或模糊查询；
- 按聚合状态筛选；
- 按制作人筛选；
- 组合筛选、清空筛选和服务端分页；
- 项目管理人可以选择当前筛选结果页中的多个未完成镜头，点击批量分配或批量重新分配后在弹窗内选择新的项目制作人员并确认；制作人下拉不常驻列表工具栏；
- 表格、卡片和故事板继续使用同一镜头列表结果；泳道时间线和甘特图共用统一排期结果。五种视图继承同一组可兼容筛选条件，不能各自定义冲突的字段语义。
- 表格筛选到具体集和具体场次，且没有关键字、状态或制作人附加筛选时，前端必须先加载完整场次，再允许项目管理人通过左侧手柄拖拽调整场内镜头位置；完整加载期间、结果超过 2000 条、卡片/故事板视图或其他查询状态均禁用拖拽，避免把页内下标误当成整场位置。完整场次加载完成后隐藏分页。
- 拖拽成功后服务端同步更新“本场第 N 镜”和 `数字镜头号`，不再要求用户额外执行重编号动作。被移动区间内只能是未分配或任务仍为 `not_started` 的镜头；任一镜头已开始制作或已有版本/文件时整体禁止拖拽。

### 8.3 五种视图

- 表格：适合批量浏览、筛选、排序和管理字段。
- 卡片：突出缩略图、镜头号、制作人、状态和最新反馈。
- 故事板：按集、场次和场内镜头顺序展示缩略图、时长和核心描述。
- 人员泳道时间线：按负责人展示镜头任务当前计划、首版基线和项目内同人撞期。
- 任务甘特图：按任务层级展示镜头任务开始、结束、真实状态和基线偏差。
- 表格、卡片和故事板点击镜头时从页面右侧打开镜头详情抽屉；泳道和甘特点击任务条时打开排期任务抽屉。两类抽屉均保留当前筛选、窗口和滚动上下文；独立详情路由继续支持深链访问和刷新恢复。

视图切换不得产生互相漂移的数据副本；原有三种视图共用镜头列表 API，两种排期视图共用统一排期 API，任务与时间事实最终都来自后端。

### 8.4 镜头增删改查

- 镜头页提供独立“新建集”和“新建场次”动作，默认建议当前范围最大编号加一；新建镜头必须指定所属集、场次和场内位置，默认追加到本场末尾。服务端自动派生连续 `数字镜头号`，前端不再提供独立镜头号输入。
- 编辑弹窗只读展示“本场第 N 镜 / 数字镜头号”，不展示 `10/20` 等内部排序键，也不允许普通编辑改号或跨场移动。普通编辑只允许未分配或任务仍为 `not_started` 的镜头；管理人员确认开工后镜头制作信息冻结，列表与详情隐藏编辑入口，后端更新接口在锁内拒绝。
- 拖拽排序走独立场内重排接口并提交目标镜头 `lockVersion`；服务端在一个事务中重排位置并同步 `数字镜头号`，成功或失败后前端都重新读取完整场次。无已冻结目录时直接改号；历史目录需改名时使用受控两阶段 NAS 迁移与审计。
- 新建镜头只创建镜头和资产关系，`storageDirName` 为空，不创建镜头目录 Outbox，不接收制作人，也不创建任务；创建完成后的聚合状态固定为“未分配”。
- 项目管理人必须通过独立的“委派任务”动作选择制作人员；第一次委派才创建唯一镜头视频任务，任务制作要求由后端从已锁定镜头制作内容建立快照。首次分配和后续改派弹窗都完整只读展示制作内容、景别、机位、镜头运动、焦段、台词/对白、音效、色调参考和备注且不得修改；后续改派只调整主制作人并更新同一任务。
- 修改镜头不得覆盖任务、版本和审核历史。
- 已产生版本后，影响业务文件名的集号、场次号、镜头号默认禁止直接修改。
- 删除采用归档和逻辑删除，不物理删除历史。单条或批量删除必须从本场最早删除位置到场尾重查任务、版本、文件和目录状态：仅无任务或任务仍为 `not_started`、无版本/文件且无冻结目录时允许；通过后在同一事务内软删除目标及其未开始任务，并把剩余镜头连续化为 `0001..NNNN`。受影响区间存在冻结目录时整体拒绝，禁止因删除而隐式迁移 NAS 目录。
- 批量分配只作用于用户当前明确勾选的镜头，不把筛选条件隐式扩展为跨页全量写入；整批必须在一个事务中完成，任一镜头状态、任务版本或制作人员资格冲突时全部回滚。

### 8.5 导入台本/镜头表

当前正式镜头样表为 `.xlsx` 工作簿，每个可见 Sheet 代表一集。Sheet 名使用 `EP001`、`EP002` 等格式；导入行不再重复填写集号。每个 Sheet 的主数据区从 `A1` 开始，固定为以下 A:O 15 列：

```text
场次、镜头号、时长(s)、镜头缩略图、制作内容描述、景别、机位、
镜头运动、焦段(mm)、场景、台词/对白、音效、色调参考、备注、镜头状态
```

其中“镜头缩略图”和“镜头状态”为只读列，导入时忽略；集号从 Sheet 名派生；场内镜头顺序从 Sheet 中同一场次的有效行相对顺序派生。样表没有角色和道具列，当前导入不得从描述或备注中猜测这两类资产。

导入必须采用“上传文件—预检查—问题修正—确认提交”流程：

- 镜头模板版本为 `shot-v3`，资源 `module_shot_grid/resources/templates/shot-v3.xlsx`，冻结 SHA-256 为 `23FF46F60BD4E52A7C3B9350F89882BB18963C92823AC40AFE601AC1553204F8`；资产模板版本为 `asset-v2`，资源 `module_shot_grid/resources/templates/asset-v2.xlsx`，冻结 SHA-256 为 `B551AC1D1D5EDC20A025B0ED90157412E1365006108816F08CB2C59AE4301696`；旧镜头 v1/v2、资产 v1 文件仅保留历史，不再由服务下载；
- 默认单文件不超过 10 MiB、业务数据不超过 10000 行、预览有效期为 1800 秒；旧模板不得被新解析器静默当作当前模板；
- 预检查逐行返回成功、警告和错误；
- Sheet 名必须匹配 `EP` 加至少三位数字；规范化后的集号在工作簿内唯一；
- `序` 固定映射为场次号 `0`、场次代码 `000`、场次名称“序”；`01场` 等正片场次规范化为正整数和至少三位代码；
- 镜头号在场内唯一，不同场次分别从 `0001` 开始；同场导入后的现有号与新号合集必须恰好为 `0001..NNNN`，不允许缺号、跳号或用 `数字镜头号` 承担稳定主键职责；
- 官方模板、预检和正式提交均不接收制作人或负责人覆盖；导入只创建镜头生产对象，全部镜头以“未分配”状态落库且不创建任务；
- 镜头预检表不展示仅供内部定位的源物理行号，但必须完整展示已解析的场次、镜头、时长、制作内容、景别、机位、镜头运动、焦段、台词、音效、色调参考、备注和场景需求；
- 场景名称已存在唯一 `Environment` 资产时直接建立关联；尚不存在时形成可追踪的待匹配资产需求，不在镜头导入中隐式创建正式资产；
- 焦段以文本保存，兼容 `135`、`35/25`、`24/18` 等样表值；
- 集数、场次数和镜头数按已成功解析出规范化结构的行去重统计，分别使用集号、“集号+场次号”和“集号+场次号+镜头号”；资产匹配错误不应缩减结构数量，`validRows`、`errorRows` 仍按行级可导入状态独立统计，也不以 Excel 原始行数作为项目数量；
- 只解析从 A1 开始的首段连续表头；样表 Q:R 之后的辅助区域不得作为镜头数据读取；
- 正式提交前重新校验数据库状态，不能只相信预检查结果；
- 正式提交仅使用 `selectedRows[{sheetName,rowNumber}]` 唯一定位多 Sheet 行，不接受 `assigneeUserId`；选中行全事务提交，任一行失败则全部回滚；
- 重复提交同一导入凭据不得重复创建数据、待匹配需求或目录操作；导入结果中的任务创建数必须为 0。

## 9. 资产管理需求

### 9.1 资产类型

MVP 只允许：

- `Character`：角色；
- `Environment`：场景；
- `Prop`：道具。

项目类型和资产类型均应使用可扩展字典，但在未评审前不得接受其他值。

### 9.2 资产字段

| 字段 | 说明 |
| --- | --- |
| 类型 | Character、Environment 或 Prop |
| 名称 | 项目内可识别的资产名称 |
| 制作分项 | 资产下独立分配和审核的图片生产单元；未分配草稿允许暂缺，分配负责人前必须补齐 |
| 资产描述 | 外观、功能、世界观或使用场景描述 |
| 任务描述 | 从当前制作分项唯一图片任务聚合或由分配时填写 |
| 备注 | 其他制作说明 |
| 状态 | 制作分项按唯一任务和版本聚合；资产按全部分项聚合，只读 |
| 制作人 | 从当前制作分项唯一任务聚合，只读；每个分项仅一名主制作人 |

资产缩略图、最新版本和使用镜头数可以作为附加只读信息展示。制作分项缩略图只使用其当前最新版本的缩略图文件，最新版本没有缩略图时不回退旧版本；父资产代表图按活动制作分项的稳定顺序选择第一张可用缩略图，不能由前端按加载先后随机选择。资产表格父行、卡片和类型看板展示这张父资产代表图；树表子行与详情分项卡片展示各自分项缩略图。资产详情头部按活动制作分项稳定顺序展示缩略图画廊，每个分项卡片标明名称和当前最新版本状态，缺图分项保留自己的占位，不得借用其他分项图片。

详情头部将资产身份、操作区与正文分开，操作按钮可换行，资产描述使用通栏，不能被按钮挤成窄列。下方分项预览按抽屉或页面的实际可用宽度自动换行，分项名称最多显示两行；已有分项状态统计时不再重复显示聚合状态标签。

资产表格采用 Element Plus 原生树形懒加载：点击资产名称旁的展开按钮后，逐行展示该资产的全部活动制作分项，包括分项名称、说明、缩略图、制作人、状态和最新版本。收起再展开复用本次查询结果；刷新后重新读取分项，项目或筛选变化不能混入旧分项。加载失败显示原因及适用的重试入口，不以空分项代替错误。

父行展示资产描述，所有分项仍共用这份描述，但列表子行不再重复展示，只显示自身“分项补充要求”，没有补充要求时显示“—”。导入预览、详情、分配、开工与制作人任务视图仍保留完整制作信息。说明默认最多三行，可展开和收起；父资产未填写时显示“暂无资产描述”，不根据分项内容推断或回填。分项数放在资产名称旁，版本放在分项缩略图下；父行仅展示状态数量汇总，子行展示自身状态。父资产操作列直接展示全部可用操作，包括详情、编辑资产、删除资产及可用时的选择分项开工，不再收进“更多”；权限与原确认流程不变。

分页和批量勾选仍以资产为单位，展开的子分项不增加资产总数，也不参与父资产批量选择。子行操作列按权限直接显示“开始任务”“分配任务/改派任务”“编辑分项”“删除分项”和“分项详情”；写操作先读取最新详情，复用原表单和确认流程，不新增整资产开工能力。归档分项继续在详情中查看。

制作分项名称缺失或只有空白时，操作列用“补齐制作分项”替代“编辑分项”；填写并保存后，刷新该分支为正常编辑及允许的分配入口。缺少可选说明、备注、缩略图或版本不会被误判为未补齐。

任一分项任务开始后（包括“目录准备中”），不能删除该分项，也不能删除父资产；已归档分项的开工历史同样阻止父资产删除。全部分项均未分配或待开工时，父资产可在满足无镜头引用、无版本、无未处理完的版本提交及原权限条件后删除。服务端在锁内复核，不能通过旧页面按钮或先归档分项绕过限制；删除不触碰 NAS 文件。

镜头列表操作列同样提供“分配任务/改派任务”，可直接打开该镜头的原分配表单；成功后刷新列表，切换项目或筛选后不允许旧操作影响当前页面。

资产和制作分项的编辑、归档、增加分项及任务分配入口必须以服务端 `allowedActions` 为准，并与平台权限取交集。项目终态、存储未就绪、资源已归档、已有版本、活动任务或未提交版本发布记录等约束由后端计算，前端不得只靠角色名或状态文案推断。

编辑资产时，全部分项未开工可调整资产描述；任一分项开工后，资产描述锁定为只读，仍允许有编辑权限的管理人员调整父资产排序和内部备注。目录准备中即视为已开工，已完成或已归档分项同样保留该约束，不能通过归档解除。只读说明旁显示原因，不隐藏整个“编辑资产”入口。旧弹窗保存期间若已有分项开工，服务端拒绝修改资产描述；弹窗恢复原说明，保留排序和备注草稿供核对后重试。独立分项的编辑、删除及父资产删除仍遵循原规则。

### 9.3 导入资产表

创建项目并成功导入镜头表后，项目管理人可以导入资产 Excel。当前正式样表主数据区是 `Sheet1!A:F`：类型、名称、描述、制作分项、备注、状态。合并单元格表示资产父级，每个有效明细行表示一个制作分项；“描述”存入父资产并供所有分项共用，不重复写入各分项。“分项补充要求”是可选独立列，没有该列就留空；“备注”逐行属于对应分项。模板不包含制作人。

正式样表共有 20 个制作分项行和 12 个逻辑资产；移除制作人列后，预检查不再因为历史复合制作人文本产生错误。Environment 为 2 个资产/4 个分项，Prop 为 4/4，Character 为 6/12；第 6—8 行缺少制作分项只产生警告。原始结构统计与用户实际选中的正式提交行数必须分开表达。

资产导入同样采用“上传文件—预检查—问题修正—确认提交”流程：

- 类型只允许 `Character`、`Environment`、`Prop` 或对应中文别名；
- 预检查按资产类型分别显示有效资产数、重复数和错误数；
- 同一项目、同一类型的规范化资产名称必须唯一；
- 制作分项允许为空，预检查只返回警告并允许正式导入，后续可以编辑补充；提交图片版本前必须存在有效制作分项；
- MVP 只新增资产或制作分项；已有同类型同名称资产可作为父级复用，但资产字段不得被 Excel 静默覆盖，冲突必须报错；
- 官方模板、预检和正式提交均不接收制作人或负责人覆盖；导入只创建资产及制作分项，全部制作分项以“未分配”状态落库且不创建任务；
- 合并单元格只在明确合并范围内继承左上角值；预检查行规范化后是自包含记录，允许选中同一父资产下的部分可导入分项；
- 正式提交后按“项目+资产类型+规范化名称”自动匹配镜头导入产生的待匹配需求；
- 只有唯一候选允许自动关联，无法匹配或存在冲突时进入人工处理列表；
- 任一选中行失败时全部回滚，重复幂等请求不得重复创建资产、制作分项、关系或目录操作；导入结果中的任务创建数必须为 0。

“根据资产表决定有多少类型”表示统计本次文件实际包含三种允许类型中的哪些类型及其数量，不表示导入文件可以自行创建新的资产类型代码。

### 9.4 镜头资产待匹配规则

- 待匹配需求保存 Excel 原始名称、规范化名称、资产类型、来源镜头和导入批次；
- 状态至少包含待匹配、已匹配、冲突和已忽略；
- 自动匹配成功后建立正式镜头资产关系，不删除来源审计信息；
- 人工选择资产或忽略需求必须记录操作者、时间和原因；
- 资产改名后不得静默重写历史原始名称，应执行受控重新匹配；
- 项目概览应分别展示总资产数与未解决的待匹配/冲突数量。

### 9.5 资产规则

- 资产名称在同一项目、同一资产类型内应唯一。
- 一个资产可以有多个制作分项；每个制作分项首次分配主制作人时创建唯一资产图片任务，改派更新原任务。
- 资产可以关联多个镜头，镜头也可以关联多个资产。
- 制作分项仅在未分配或任务仍为 `not_started` 且未产生版本时允许补充或纠正；制作人开始任务后立即禁止普通修改，不等待首个版本提交，也不得自动改写历史业务文件名。
- 资产归档前必须提示其被哪些镜头使用；不得级联删除镜头关系之外的历史版本和审核记录。

## 10. 任务管理需求

### 10.1 任务类型与唯一性

| 任务类型 | 归属 | 产出物 |
| --- | --- | --- |
| `shot_video` | 一个镜头 | MP4 或 MOV 视频 |
| `asset_image` | 一个资产制作分项 | JPG 或 PNG 图片 |

- 一个镜头最多有一个正式 `shot_video` 任务。
- 一个资产制作分项最多有一个正式 `asset_image` 任务。
- 一个任务不能同时属于镜头和资产制作分项，也不能成为无归属任务。
- 首次分配制作人时创建任务；后续改派更新同一任务并记录审计。
- 镜头和资产制作分项仅在未开工时可普通改派。未分配时可分配任务，待开工时可改派；目录准备中、制作中、待审核、修改中和已完成时不显示普通改派按钮，管理人员亦不可绕过。
- 单个和批量分配均由后端重新核对状态与锁版本，批量中任何任务已经开工则整批失败，不跳过、不部分改派；资产按全部活动分项是否可分配决定父级批量入口。已开工任务不重置，交接和返工重开须作为后续独立流程设计。

### 10.2 任务字段

任务至少包含：任务类型、所属项目、所属镜头或资产、负责人、任务描述、优先级、当前预期开始/结束时间、首次排期基线、兼容截止日期、状态、最新版本、最终版本和审计信息。当前时间与基线均不替代状态，结构化改期历史见第 10.5 节。

### 10.3 任务状态流转

```text
待开工 not_started
  └── 开始镜头或资产任务 ──→ 目录准备中 preparing

目录准备中 preparing
  └── 目录 Outbox 成功 ──→ 制作中 in_progress

制作中 in_progress
  └── 上传并提交版本 ──→ 待审核 pending_review

待审核 pending_review
  ├── 确认通过 ──→ 已完成 completed
  ├── 退回修改 ──→ 修改中 revision
  └── 稍后决定 ──→ 待审核 pending_review

修改中 revision
  └── 上传并提交新版本 ──→ 待审核 pending_review
```

不允许普通用户任意修改状态代码。每次状态变化必须由明确业务动作触发并记录操作人、时间和原因。

资产树表父行的“时间状态”汇总全部活动且未删除的制作分项，同类合并为“正常 2”等标签，混合状态按已延期、临近结束、正常、未设置时间、已完成排序。无分项显示“—”，已完成分项不再计入催办。收起时也显示完整统计，每 30 秒及恢复页面可见时重算；时间经过只更新提醒，不自动开工、完成或阻止提交。父行开始、结束时间仍显示“—”，具体时间在各分项行查看。

### 10.4 我的任务

制作人员必须能够查看：

- 分配给自己的待开工、目录准备中、制作中、待审核和修改中任务；
- 任务所属项目、镜头或资产、截止日期和优先级；镜头任务必须完整展示制作内容、景别、机位、镜头运动、焦段、台词/对白、音效、色调参考和备注，任务存在另行调整的要求时再独立展示补充要求；
- 历史版本、当前版本状态和下一步动作；
- 当前全部未关闭修改问题，包括来源版本、文字、画面标注或视频时间点；
- 每条问题在此前版本上的制作处理说明和审核确认结果；
- 提交修订版本时，为本轮全部 open 问题逐条填写处理说明。

当前真实前端工作台使用 `GET /shot-grid/tasks/mine`，负责人范围由后端按当前账号强制注入；支持任务类型、状态、优先级、截止日期区间、关键字、排序和服务端分页。任务行进入 `/tasks/:taskId`，详情接入真实查询、编辑和等待开工；任务要求、优先级和截止日期只允许项目管理人在 `not_started` 时编辑，镜头或资产制作分项由管理人员确认开工后即锁定，前端隐藏入口且后端更新接口返回 409。路由切换、刷新和同一任务 ID 的 ABA 往返必须通过中止请求和 generation 校验隔离迟到响应。

两类任务的制作人只读查看“待开工”任务，等待管理人员确认；进入制作中后才能提交。资产由管理人员按制作分项独立确认，不提供整资产或批量开工；一个分项的开工不改变其他分项。依赖及开工条件暂由管理人员线下确认，不增加自动检查、暂停或撤销能力。

资产列表与详情返回 `itemStatusCounts`，固定包含 `unassigned/not_started/preparing/in_progress/reviewing/revision/completed` 七个非负整数键，仅统计活动且未删除分项。父级状态按 `revision → reviewing → in_progress → preparing → unassigned → not_started` 聚合；至少有一个活动分项且全部完成才为 `completed`，无活动分项为 `unassigned`。父级 `task.start` 仅表示可进入分项选择，至少存在一个实际可开工分项才返回；真正 start 必须对选中分项任务提交，不能整资产开工。

镜头和资产列表原有三种视图、工作台及任务/资产详情复用有界状态查询：待开工每 5 秒，目录准备中每 1.5 秒且每轮最多 80 次；资产列表依据 `itemStatusCounts`，不能因父级为制作中而漏掉其他待开工/准备中分项。仅查询已确认的筛选、分页和排序；保留当前内容与有效勾选，列表及资产详情在筛选草稿、相关弹窗或写入期间暂停；任务详情保留编辑快照且不替换锁号，切项目/路由和卸载中止请求并隔离迟到响应。连续 3 次失败或归一化 401/403/404 停止并提示人工刷新；当前结果无待开工/准备中项时停止。轮询只读取服务端状态，不触发开工。两种排期视图首版不增加状态轮询或 WebSocket，改期成功后只定向刷新任务与受影响泳道。

### 10.5 项目排期与人员规划

- 镜头列表新增人员泳道时间线和任务甘特图，保留表格、卡片和分镜板；资产列表新增相同两种排期视图，保留表格、卡片和类型看板。项目列表或项目详情提供综合排期深层入口，在同一页面查看镜头与资产制作分项任务，不新增一级导航。
- 人员泳道默认按负责人分组，用于查看当前项目“谁在什么时间做什么”和同人任务撞期；任务甘特默认按任务层级分组，用于查看开始、结束、首版基线和当前计划偏差。两种模式共用筛选、日/周/月缩放、基线、冲突、未排期池和编辑流程，不建立两套数据源。
- 排期按自然时间连续计算，周末和节假日均可安排。系统不计算每日工时、人员容量或跨项目负载，不建立任务依赖、关键路径或自动顺延，也不展示无法由正式数据证明的完成百分比。
- `expectedStartTime/expectedEndTime` 是当前排期。任务第一次取得完整排期时冻结首版基线；后续改期只更新当前排期，并记录操作人、时间、原因、前后范围、锁版本和冲突确认快照。迁移时已有完整排期只冻结为基线，不伪造原始改期历史；无排期任务保持为空。
- 具备 `shotgrid:task:schedule` 且为项目 `director` 或 `has_all_scope` 的管理人员可以改期，制作人员只读。页面默认只读，管理人员显式进入编辑模式后可水平拖动、调整起止边界或用 Element Plus 表单精确修改；拖入其他人员泳道必须回弹，负责人仍通过现有受控委派/改派流程改变。
- 同项目同负责人未完成活动任务的当前计划按 `[start,end)` 判断重叠。冲突只警告，后端返回最新集合，用户二次确认后允许保存；集合或任务锁版本变化时必须重新确认或刷新。改期不得改变任务状态、负责人、开工、目录、版本、审核或提交权限。
- 未排期池只包含已经委派并存在真实任务、但尚无完整当前排期的任务。未委派镜头或资产制作分项继续显示“未分配”，必须先完成委派，不能为排期页面创建虚拟任务。

## 11. 版本与文件命名规则

### 11.1 版本通用规则

- 每次正式提交是一个不可拆分的“版本轮次”，必须创建一个新版本；版本从 `V001` 开始在任务范围内连续递增。
- 一个版本轮次允许提交 `1..N` 个候选作品。候选在轮次内从 `01` 连续编号，展示为 `V001_01`、`V001_02`；只提交一个文件时仍是 `V001_01`。
- `V001` 是审核、返修和版本统计的业务轮次，`01/02` 是该轮候选小编号；候选数量不得增加版本计数，候选也不得被拆成多个 `sg_version`。
- 版本号由后端在并发安全的事务中分配，前端不能根据列表长度计算。
- 已提交轮次及其中全部候选不可覆盖、替换或删除；修订必须提交下一版本轮次。
- 版本必须记录提交人、提交时间和修改说明；每个候选必须独立记录源文件、业务文件名、摘要、大小、顺序和可选候选说明。
- 第一版的修改说明用于描述本次交付；修订版本除全局修改说明外，还必须为提交时全部 open 修改问题逐条保存处理说明。全局说明不能替代逐条说明。
- 同一任务同时只能存在一个最终版本。
- 同一轮全部候选共享一个由服务器生成的 Unix 毫秒批次时间戳，仅作内部元数据，不拼入新文件名；候选顺序按创建命令中的稳定顺序冻结，不能按上传完成先后编号。
- 单候选轮次由系统直接将唯一文件设为“本轮最佳候选”，审核人直接播放检查并保存问题、退回或确认通过；多候选轮次必须先由审核人选定一个“本轮最佳候选”。问题、标注、历史问题确认和最终版本都精确绑定该候选。
- 镜头与资产列表、详情、卡片和故事板需要在多候选审核选择前提供稳定预览：尚未选择最佳候选时展示候选 01，选择后立即切换为当前最佳候选；业务文件名、缩略图和代理媒体必须来自同一候选。正常的待审核状态不得因为暂时没有主审核媒体而阻断整个镜头列表，也不得让资产列表或详情丢失缩略图。
- 审核通过后，原候选文件和全部同轮候选保持原位且不可覆盖。系统在任务现有 NAS 目录下异步生成唯一 `FINAL/` 子目录，其中以原业务文件名发布被选中的最佳候选，并写入 `FINAL.json`；用户可同时通过目录名和清单确认哪个文件是最终版本。
- 审核事务成功表示数据库已经确认最终版本并创建最终交付队列，不等于 SMB I/O 已完成。页面必须区分 `pending/publishing/published/failed`，只有 `published` 才能显示“最终版本已发布到 NAS”。

### 11.2 镜头视频文件名

规范：

```text
{项目代号}_EP{集号至少3位}_{场次号至少3位}_{镜头号至少4位}_{制作人用户昵称}_V{版本号至少3位}_{候选号至少2位}.{mp4|mov}
```

示例：

```text
WGZR_EP001_001_0001_YJF_V001_01.mp4
```

“序”中的镜头使用场次代码 `000`，例如：

```text
WGZR_EP001_000_0001_YJF_V001_01.mp4
```

字段含义：

- `WGZR`：项目代号；
- `EP001`：第一集；
- `001`：第一场；
- `0001`：第一个镜头；
- `YJF`：制作人的平台用户昵称；
- `V001`：任务的第一个正式版本；
- `01`：该版本轮次内的第一个候选。

镜头业务文件名包含 `V001/V002`，并且必须与后端任务范围内连续生成的正式版本号、审核单和页面展示一致。

### 11.3 资产图片文件名

规范：

```text
{项目代号}_Asset_{Character|Environment|Prop}_{安全资产名称}_{安全制作分项}_{制作人用户昵称}_V{版本号至少3位}_{候选号至少2位}.{jpg|png}
```

示例：

```text
WGZR_Asset_Environment_动力舱室内_动力舱恐怖气氛主视角_YJF_V001_01.jpg
```

### 11.4 命名约束

- 项目代号、制作人平台用户昵称、版本号和候选号均使用提交时已确认的服务端值；镜头和资产新文件名都以版本号、候选号及扩展名结尾，不再追加时间戳。
- 文件扩展名统一转为小写，并与实际媒体类型一致。
- 资产名称和制作分项进入文件名之前必须按路径安全规则校验，但不得静默替换成无法追溯的名称。
- 相同版本轮次不得因重复请求生成第二个时间戳；同一幂等命令的每个候选必须复用原候选号和业务文件名。
- 历史文件名在项目、成员、资产改名或命名规则变更后保持不变；已有带时间戳提交的重试仍复用原文件名和路径。NAS 已有文件仅在大小及摘要一致时幂等复用，不同内容必须拒绝覆盖。
- 平台内部物理存储名与业务文件名是两个概念；页面和 NAS 使用业务文件名，平台文件基座仍保留稳定 `fileId`、摘要和业务引用。

### 11.5 文件校验

- 镜头任务只接受 MP4、MOV；资产任务只接受 JPG、PNG。
- 后端必须同时校验扩展名、声明的 MIME 类型和实际文件内容，不能只信任浏览器上传值。
- 初始配置每轮允许 `1..10` 个候选，单文件最大 `100 MiB`、整轮最大 `500 MiB`；三个上限均由后端配置并通过 preflight 能力响应返回，前端不得只硬编码文案。视频编码、图片分辨率和视频时长限制属于后续部署参数。
- 同一轮所有候选必须属于任务要求的同一媒体族；同一批次内 SHA-256 完全相同的重复内容必须拒绝。
- 失败上传、未被版本引用的临时文件必须纳入保留、回收和对账机制。

### 11.6 版本上传与恢复交互

制作人界面必须按业务阶段使用不同的行动文案：零版本任务显示“提交首版成果 / 提交首版并进入审核”，退回修改任务显示“提交修改成果 / 提交修改成果并重新送审”，并明确提示即将生成的 `Vnnn`。不得始终使用“提交新版本”让制作人自行判断当前是在首次交付还是返修送审。

版本上传必须严格执行：

```text
本地候选文件/任务校验
→ private preflight（ordered candidates/changelog/aiParams/issueResponses）
→ 逐个调用平台私有文件上传并取得各自 fileId
→ create HTTP 202（ordered candidates/fileIds/changelog/aiParams/issueResponses + X-Idempotency-Key）
→ current/状态查询
→ 仅 committed 显示成功
```

- 首版提交没有历史 open 问题，`issueResponses` 必须为空；修订提交必须恰好覆盖当前任务全部 open 问题，每项包含 `issueId` 和非空 `responseText`，不得遗漏、重复、夹带已关闭问题或引用其他任务的问题。
- preflight 的 `candidates` 按用户确认顺序提交，每项包含稳定的 `clientFileKey/fileName/fileSize/sortOrder/candidateNote`；create 必须按同一顺序回传 `clientFileKey/fileId/sortOrder/candidateNote`。后端以该顺序分配连续候选号，幂等命令哈希必须包含完整有序候选列表，顺序变化属于不同命令。
- preflight 是无锁、无写库、无文件副作用的尽早拒绝；它校验当前用户正是任务当前委派的活动 `creator`、完整上下文、open 问题集合与逐条说明覆盖、未解决提交、扩展名、业务文件名、目标相对路径可生成和目录快照字段完整；`director`、管理员、超级管理员和全项目数据范围均不能绕过该本人门禁。preflight 不访问 NAS、不检查实际目标文件、不预留版本号或承诺 create 成功。实际目标文件冲突由 Worker 无覆盖发布阶段处理。
- preflight 失败、权限撤销、任务切换、用户换文件或任务/文件 ABA 时必须零上传；真实媒体字节/签名只能在上传后检查。
- create 必须在上传后锁定项目和任务，全量重检当前用户仍是任务当前委派的活动 `creator`、任务状态、当前 open 问题集合、逐条说明覆盖、未解决提交、稳定目录和源文件授权/摘要/大小，关闭 preflight 与 create 之间的 TOCTOU 窗口。若负责人、成员状态或问题集合在 preflight 后发生变化，必须拒绝并要求制作人重新进入当前任务，不能静默代提交或接受过期说明。
- 刷新任务详情时通过 `current` 恢复未解决提交。自动轮询单轮最多 30 次、连续错误 3 次暂停、指数退避有上限；401/403/404 停止，终态允许手工刷新。
- `pending/publishing/published/committing` 都是处理中，`committed` 是唯一成功；`failed` 仍占用任务且只能重试原行，不能新建第二条提交。
- create 结果未知时，复用当前内存中的原有序 `fileId` 列表、逐条问题处理说明和幂等键重放 create，跳过 preflight 和上传；同键异请求拒绝。`fileId`、幂等键、修改说明、逐条问题处理说明和 AI 参数不得持久化到浏览器存储。
- Worker 可以逐个发布候选，但只有全部候选均完成无覆盖发布后，才能在一个短事务创建一个正式版本轮次、全部候选、候选文件关系和一个自动审核单；任一候选失败时不得向版本历史暴露半个轮次。
- 版本历史、版本详情和受保护下载使用真实接口；`/versions/:versionId` 归属 `reviews` 路由范围。下载保留 Range/416，Blob JSON 错误只做有界解析并保留业务 `errorKey/details`，临时 Object URL 用后释放。
- 平台上传成功但业务引用尚未建立即失败的孤儿私有文件，必须由平台保留、对账和回收机制治理，前端不得盲目永久删除。

## 12. 审核单、跨版本修改问题与审核动作

### 12.1 自动审核单

- 每次版本轮次提交成功，必须自动创建一个只包含当前版本轮次的审核单；候选文件不是独立审核单条目。
- 版本创建、文件引用、自动审核单创建和任务进入待审核必须形成一个一致的业务结果。
- 退回后重新提交新版本，必须生成新的审核单；旧版本、旧意见和旧审核单不得覆盖。
- 单候选审核单自动将唯一文件认定为本轮最佳，审核页不显示候选选择区，直接进入播放检查、问题记录和结论提交；多候选审核单初始不认定最佳，审核人先浏览全部候选，再显式选择且仅选择一个最佳候选。多候选没有选择时不能创建/保存问题草稿，也不能通过或退回。
- 没有任何问题草稿时允许切换最佳候选；一旦当前候选存在服务端问题草稿，必须先删除草稿才能切换，禁止把时间点或画面标注静默迁移到另一个候选。`defer` 保留当前选择和草稿。
- 审核通过或退回后，本轮最佳候选立即冻结：前端仅在已选候选上保留不可操作的“本轮最佳”状态，隐藏其他候选的选择按钮，避免制造仍可切换的心智干扰；后端继续拒绝非 `pending_review + active` 状态的选择请求。历史候选画面仍允许预览和下载，但不得改变已发布问题或最终结论绑定的候选。

### 12.2 人工批量审核单

项目管理人或管理员可以将同一项目的多个待审核版本加入人工批量审核单，并按明确顺序连续审核。人工批量审核单不改变版本原本所属的自动审核单和任务。

### 12.3 修改问题

- 面向用户的正式名称为“修改问题”，现有接口或表中的 `Note/sg_note` 仅作为迁移期兼容名称。
- 每条问题必须绑定首次提出它的来源版本轮次、来源候选和创建人；来源候选创建后不可修改。问题在后续版本中继续显示，不代表它被复制或迁移到了新版本或其他候选。
- 每条问题必须至少包含非空文字内容或一组有效画面标注，也可以两者都有；不能提交既无文字又无标注的空问题。
- 视频问题可以绑定整数毫秒时间点；图片或视频画面标注使用 `0..1` 归一化坐标，并记录标注类型、颜色、点集和创建时媒体尺寸。审核画面提供点、框选、箭头、涂抹和文字五种标注方式；涂抹轨迹在拖动过程中实时显示，松开后才作为一条 `freehand` 标注写入当前问题草稿。
- 每条问题可以添加可选“参考内容”，用于附带效果示例图片、本地文档、表格、演示文稿、文本或短视频，使制作人同时看到问题、修改目标和可对照资料。每条最多 5 个文件、单个不超过 20 MiB；图片在问题卡片中直接显示缩略预览，其他资料显示名称、大小和受控下载入口。
- MVP 中所有 open 问题都是需要处理的阻塞项，不区分“普通评论”和“必须修改”，数据模型和 API 不再保留 `isMandatory`。
- 问题状态只允许 `open` 和 `resolved`。普通 CRUD、制作人回复或页面按钮都不能直接解决问题；只有审核人在后续版本上确认 `resolved` 时才能关闭，并记录实际解决它的 `resolvedInVersionId`。
- open 问题的 `pendingVersionId/pendingVersionNumber` 表示制作人下一轮工作的基线版本：新问题等于来源版本；历史问题被确认 `still_present` 后等于本次被退回版本。该派生归属不改写原始问题和标注。
- 切换版本或候选后，本地未保存内容不能错误提交到旧上下文；点击“保存问题草稿”后，内容进入当前自动审核单、当前最佳候选的服务端私有草稿，制作人、任务问题列表和生产履历均不可见。
- 审核单仍为待审核时，授权审核人可以携带乐观锁版本编辑或删除问题草稿；点击“退回并发送问题”是唯一发布边界，后端在同一事务把当前审核单全部草稿转换为正式 `sg_note` 并删除草稿。
- 参考内容与所属问题遵循同一可见性边界：保存草稿后仅审核方可见，编辑草稿时全量替换引用，删除草稿时解除引用；执行退回后才与正式问题一起对制作人公开。文件必须保存为平台受保护文件，制作人只能通过校验项目成员关系和问题引用的专用接口查看或下载。
- 正式问题发布后，正文、来源版本、时间点和标注不可覆盖，也不提供删除动作；后续只能通过版本处理说明和审核确认推进状态。
- 审核页点击正式问题或草稿的“查看对应作品”时，若问题属于当前版本，必须先按其 `originCandidateId/candidateId` 自动切换到绑定候选，再定位时间点和画面标注；跨版本问题继续进入原版本对比流程，不得把旧版本候选 ID 套用到当前版本。

### 12.4 制作人逐条处理说明

- 任务被退回后，制作人在 `/tasks/:taskId` 查看当前全部 open 问题及其来源版本、文字、标注和时间点。
- 任务详情的历史版本文件列表必须按候选提供“预览”入口；退回反馈区占用主预览位置时，制作人可在弹窗中逐个播放对应候选，优先使用受保护的代理媒体，且不得向页面暴露 NAS 或对象存储物理路径。
- 提交下一版本时，制作人必须对当时全部 open 问题逐条填写“本版如何处理”；一条问题对应一条处理说明。
- 处理说明必须绑定“本次新版本 + 原问题 + 提交人”，与新版本一起原子持久化，并作为不可变历史保留。
- 全局本轮修改说明用于概括本次提交，不能代替逐条处理说明；制作人声明“已修改”也不会自动关闭问题。
- “意见回复/沟通记录”不属于本轮 MVP；旧回复和旧意见数据直接清理，不提供聊天式回复或兼容读取入口。

### 12.5 审核人逐条确认

审核人在审核 V002 及后续版本时，单候选由系统直接确定本轮最佳，多候选先由审核人选定本轮最佳，再完成两类工作：

1. 对从历史版本带入的每一条 open 问题，结合来源版本标注、制作人的本版处理说明和当前媒体，逐条确认：
   - `resolved`：当前最佳候选已修复，关闭问题并记录 `resolvedInVersionId=当前版本` 及 `checkedCandidateId=当前最佳候选`；
   - `still_present`：当前版本仍存在，必须填写具体未解决原因；问题保持 open，退回后将待处理归属推进到当前版本。
2. 检查当前版本是否还有新的问题；新问题始终绑定当前版本，并按 12.3 的规则提交。

确认结果绑定“问题 + 当前被审核版本 + 当前最佳候选 + 审核人”，不可覆盖历史确认。`resolved` 不需要补充说明，`still_present` 必须填写原因。历史问题即使跨 V002、V003 多轮仍只保留一个问题身份，通过各版本候选上的确认记录展示演进过程。

### 12.6 审核动作

| 动作 | 代码 | 前置条件 | 结果 |
| --- | --- | --- | --- |
| 确认通过 | `approve` | 版本待审核；所有带入问题均已在当前版本确认 `resolved`；不存在 open 问题或待发布草稿 | 当前版本成为最终版，任务完成 |
| 退回并发送问题 | `reject` | 版本待审核；所有带入问题均已逐条确认；至少存在一条 `still_present`、当前版本既有正式问题或问题草稿 | 草稿原子发布为不可变正式问题；版本已退回，任务进入修改中，制作人首次可见本轮问题 |
| 稍后决定 | `defer` | 版本待审核 | 仅记录动作，版本和任务保持待审核，问题草稿继续仅审核方可见 |

`reason` 只能作为审核动作总述，不能替代结构化修改问题。审核动作必须是不可变历史；问题确认、问题状态、版本、自动审核单和任务状态必须在审核事务中保持一致。并发审核时，后到请求必须得到明确冲突提示，不能产生两个最终版本、遗漏问题确认或将已完成任务重新改为修改中。

`approve` 还必须在同一数据库事务创建与该最终版本一对一的最终交付 Outbox，冻结最佳候选、源 NAS 相对路径、摘要、大小、目标 `FINAL/` 路径、清单路径和审核人。审核请求内禁止访问 NAS；Application Leader 上的版本 Worker 按“短事务领取 → 事务外硬链接或校验复制 → 无覆盖发布文件和 `FINAL.json` → 短事务结果回写”完成投影。硬链接不可用时允许回退为复制，但两种方式都必须重算摘要和大小；已有同内容目标按幂等重用，已有不同内容目标必须失败关闭，不能覆盖。

### 12.7 正式审核循环

```text
分配任务
→ 制作人员在线下制作
→ 上传并提交 V001
→ 自动创建 V001 审核单
→ 项目管理人审核
   ├── 满意且无 open 问题：V001 为最终版，任务完成
   ├── 稍后决定：继续待审核
   └── 保存一条或多条 V001 问题草稿并点击“退回并发送问题”
       → 草稿原子发布为 V001 正式修改问题，制作人此时首次可见
       → 任务进入修改中
       → 制作人员查看全部 open 问题并线下修改
       → 对每条 open 问题填写处理说明
       → 上传并提交 V002，处理说明与 V002 一起保存
       → 自动创建 V002 审核单
       → 项目管理人审核 V002
          ├── 逐条确认 V001 问题为 resolved 或 still_present
          ├── 可提出绑定 V002 的新问题
          ├── 全部历史问题已解决且无新问题：通过 V002，任务完成
          └── 仍有旧问题或存在新问题：退回，全部未关闭问题的待处理归属为 V002，制作人据此制作并提交 V003
```

示例：V001 的问题 A、B 中，V002 确认 A 已解决、B 仍存在，同时在 V002 新增问题 C；退回后 B、C 都作为 V002 的当前待处理问题，制作人基于 V002 修改并提交 V003。V001 下的 B 只显示“已处理但未通过，待处理已转入 V002”；B 的来源和原始标注仍为 V001，不复制问题。A 仍保留在历史中，来源版本为 V001，解决版本为 V002。

### 12.8 新基线与当前实现边界

本节从 2026-08-14 起作为正式业务基线，并于 2026-08-21 增加“审核私有草稿 → 退回时正式发布”边界，覆盖此前“普通评论/必须修改、聊天式回复、制作人或审核人独立点解决”的旧流程。数据库迁移、接口、制作人任务页和审核页功能代码已按新模型实现；用户手动业务旅程尚未执行前，不得描述为完整验收通过。

### 12.9 镜头与资产生产履历

镜头和资产详情必须提供统一的“生产履历”聚合视图，使项目管理人和制作人员在同一页面理解“创建/导入 → 委派 → 制作 → 提交版本 → 审核 → 完成”的当前进度和真实历史，而不需要分别翻查任务、版本和审核页面。

#### 12.9.1 信息层级

生产履历固定采用两层结构，并使用 Element Plus 2.14.3 的真实组件契约实现：

1. 顶部使用 `ElSteps/ElStep` 只表达当前所处阶段，使用六个用户可理解的步骤：`创建/导入`、`委派`、`制作`、`提交版本`、`审核`、`完成`；
2. 下方使用 `ElTimeline/ElTimelineItem` 表达已经发生的记录。版本是制作与审核循环的主节点，每个版本节点使用 `ElCollapse/ElCollapseItem` 展开本版审核动作、本版提出的问题、本版提交时对历史问题的处理说明，以及本版审核时对历史问题的确认结果。

阶段条不是审计历史，不得把每一次“退回 → 修改 → 再提交”重复铺成新的线性步骤。返修中的对象仍停留在“审核”步骤，并通过版本时间线展示 V001、V002、V003 等循环。

服务端阶段码固定为：

| `currentStage` | `activeStep` | 页面含义 |
| --- | ---: | --- |
| `created` | 0 | 来源对象已经建立，尚无正式任务 |
| `assigned` | 1 | 已存在任务，尚未开始制作 |
| `production` | 2 | 正在制作或准备提交版本 |
| `review` | 4 | 已提交不可变版本，当前版本待审核；步骤 3“提交版本”已完成 |
| `revision` | 4 | 审核退回后的制作—提交—审核循环；时间线展示每轮实际节点，不把返修伪装成新的主流程 |
| `final` | 5 | 已确认最终版本且任务完成 |

镜头只有一个镜头视频任务，因此直接展示单条履历。资产可以有多个制作分项，必须把每个未逻辑删除的制作分项作为独立履历泳道，并保留其 `active|archived` 业务生命周期标识：资产页使用 `ElTabs/ElTabPane` 先展示“全部分项”摘要，再由用户切换到具体分项查看时间线；“全部分项”只做汇总，不得把不同分项的版本和问题混排为一条看似连续的历史。资产顶部当前阶段只由活动泳道决定；归档泳道仍保留历史，但不得阻塞当前项目进度。列表类视图的父资产代表缩略图只能从活动泳道选择；资产详情顶部逐一展示全部活动泳道的当前缩略图，没有缩略图的活动泳道显示独立空态，不得用归档分项旧图或其他分项图片冒充。

#### 12.9.2 证据与历史真实性

履历事件必须标记 `evidenceLevel=confirmed|inferred`：

- `confirmed` 仅用于可由当前正式业务表直接证明的对象创建、手工新增资产制作分项、明确来源批次、正式版本、审核动作、修改问题、处理说明和审核确认；
- `inferred` 只用于根据现有记录推断的节点，页面必须显示“按现有记录推断”，不得使用与确认事件相同的确定性文案；
- 第一版现有任务的 `createTime` 只能证明任务记录何时建立，不能证明该时刻已经发生可审计的首次委派命令、开始制作或改派，因此只可显示为推断的“建立制作任务”；即使当前业务规定第一次委派创建任务，也不得据此改写无法证明来源命令的历史数据；
- 资产制作分项存在明确 `sourceImportBatchId` 时显示导入来源；来源批次为空时，才以分项自身的 `createTime/createBy` 显示确认的“手工新增制作分项”，两类来源不得重复。不得因对象当前存在，就推断它一定来自 Excel；镜头不根据名称、创建时间或其他旁证伪造导入事件；
- 当前数据不能重建的旧改派、旧开始、暂停或恢复历史必须明确缺省，不能用当前负责人、任务更新时间或通用操作日志反推并补写为历史事实。

第一版生产履历是对既有正式表的只读聚合，不新增事件表或迁移。后续如需要完整记录每次委派、改派、开始、暂停、恢复及来源命令，可增加 append-only 的 `sg_production_event` 领域事件表；该表是后续增强项，不是本版已经实现或可从历史数据自动回填的能力。未新增该表前，六阶段是聚合进度，不是六条已确认审计事件。

#### 12.9.3 可展开内容与详情跳转

每个版本循环必须区分以下四类不可混写的事实：

- `reviewActions`：对该版本执行的通过、退回或稍后决定；
- `sourceIssues`：首次在该版本提出的问题；
- `issueResponses`：提交该版本时，制作人对历史 open 问题填写的逐条处理说明；
- `issueVerifications`：审核该版本时，对历史问题记录的 `resolved` 或 `still_present` 确认。

不得把处理说明或确认结果错误嵌入来源问题并改写成“问题自身的状态日志”，也不得把一个跨版本问题复制到每个版本。问题身份和来源版本继续遵守第 12.3—12.5 节。

履历节点在目标存在且当前用户有权访问时提供站内深链：

- 任务节点进入 `/tasks/:taskId`；
- 版本节点进入 `/versions/:versionId`；
- 自动审核单或审核动作进入 `/reviews/:reviewListId`；
- 问题的文字、时间点、标注数量和状态摘要直接在版本节点内展开；原始结构化画面标注只在审核详情按权限读取。问题和审核动作如需进入详情，统一通过所属自动审核单进入 `/reviews/:reviewListId`。当前审核页没有按问题定位能力，只有实际实现并验证后才能增加 `issueId` 深链；
- 导入批次当前没有独立业务端详情路由，因此第一版只展示来源摘要，不伪造不可用跳转。

前端必须使用 Vue Router 站内导航，不得直接拼接浏览器地址或根据隐藏字段推断权限。后端不返回前端路由字符串，只返回稳定资源标识和关联对象。

#### 12.9.4 读取权限与内容完整性

生产履历不是只含镜头或资产主数据的普通详情，而是一次完整返回任务、版本、审核单、审核动作和修改问题的复合读模型。后端必须在 `PreAuth` 和 `ProjectAccess` 之外，对平台权限执行严格 AND：

- 镜头履历：`shotgrid:shot:query`、`shotgrid:version:query`、`shotgrid:reviewList:query`、`shotgrid:note:list`；
- 资产履历：`shotgrid:asset:query`、`shotgrid:version:query`、`shotgrid:reviewList:query`、`shotgrid:note:list`。

任一项缺失时拒绝整个履历请求，前端进入无权限状态；不得只凭对象查询权限获取版本、审核或问题内容，也不得由前端隐藏区域来替代后端鉴权。第一版不采用字段级静默裁剪，因为缺少版本、审核或问题后，阶段、计数和版本循环都会形成误导性的残缺履历。原始结构化画面标注仍不包含在生产履历中，只能在通过审核详情权限校验后读取。

#### 12.9.5 页面状态与刷新

生产履历必须使用 `ElSkeleton`、`ElAlert`、`ElEmpty` 和 `ElButton` 的真实状态契约实现加载骨架、空历史、失败提示、无权限、资源不存在和可控重试。5xx 不得伪装成空时间线；401/403/404 应按统一请求层语义处理，不能对明确无权限或不存在的资源无意义自动重试。镜头、资产、制作分项或路由参数切换时必须取消旧请求并使用 generation 隔离迟到响应，避免把上一对象的履历显示到当前详情。

## 13. 项目概览与统计口径

### 13.1 概览字段

项目概览至少展示：

- 项目当前阶段；
- 总集数；
- 总场次数；
- 总镜头数；
- 总资产数；
- 总制作分项数；
- 镜头完成数；
- 资产完成数；
- 制作分项完成数；
- 待审核镜头数；
- 待审核资产数；
- 待审核制作分项数；
- 正在修改中的镜头数；
- 正在修改中的资产数；
- 正在修改中的制作分项数；
- 未分配镜头数；
- 未分配资产数；
- 未分配制作分项数；
- 整体完成度。

### 13.2 统计规则

| 指标 | 计算口径 |
| --- | --- |
| 总集数 | 当前项目中未逻辑删除、未归档的集数量 |
| 总场次数 | 当前项目中未逻辑删除、未归档的场次数量 |
| 总镜头数 | 当前项目中未逻辑删除、未归档的镜头数量 |
| 总资产数 | 当前项目中未逻辑删除、未归档的资产数量 |
| 镜头完成数 | 聚合状态为 `completed` 且存在最终版本的镜头数量 |
| 总制作分项数 | 当前项目中未逻辑删除、未归档的资产制作分项数量 |
| 资产完成数 | 至少有一个活动制作分项，且所有活动制作分项均已完成并存在最终版本的资产数量 |
| 制作分项完成数 | 唯一任务为 `completed` 且存在最终版本的制作分项数量 |
| 待审核镜头数 | 唯一任务状态为 `pending_review` 的镜头数量 |
| 待审核资产数 | 至少一个制作分项任务为 `pending_review` 的资产数量 |
| 待审核制作分项数 | 唯一任务状态为 `pending_review` 的制作分项数量 |
| 修改中镜头数 | 唯一任务状态为 `revision` 的镜头数量 |
| 修改中资产数 | 至少一个制作分项任务为 `revision` 的资产数量 |
| 修改中制作分项数 | 唯一任务状态为 `revision` 的制作分项数量 |
| 未分配镜头数 | 尚未创建唯一任务的镜头数量 |
| 未分配资产数 | 至少一个活动制作分项尚未创建任务的资产数量 |
| 未分配制作分项数 | 尚未创建唯一任务的资产制作分项数量 |

整体完成度默认采用等对象权重：

```text
整体完成度 = (镜头完成数 + 制作分项完成数) ÷ (总镜头数 + 总制作分项数) × 100%
```

- 分母为 0 时显示 `0%`，不得显示 `NaN` 或 `100%`。
- 结果保留一位小数或按统一界面规则取整。
- 所有统计必须来自后端统一聚合口径，不能由前端对当前分页数据自行累加。
- 已归档、逻辑删除或不纳入交付的对象是否计入统计必须由明确字段决定。

### 13.3 镜头、制作分项和资产聚合状态

| 代码 | 中文 | 计算条件 |
| --- | --- | --- |
| `unassigned` | 未分配 | 尚无正式任务 |
| `not_started` | 待开工 | 唯一任务等待管理人员确认 |
| `preparing` | 目录准备中 | 已确认开工，等待目录成功 |
| `in_progress` | 制作中 | 唯一任务为制作中 |
| `reviewing` | 审核中 | 唯一任务为待审核 |
| `revision` | 修改中 | 唯一任务为修改中 |
| `completed` | 已完成 | 唯一任务已完成且存在最终版本 |

普通成员不能手动设置聚合状态。

上表直接用于镜头和制作分项。资产包含多个活动制作分项时，全部分项完成且均存在最终版本才聚合为 `completed`；否则按 `revision`、`reviewing`、`in_progress`、`unassigned`、`not_started` 的优先顺序返回需要处理的状态。

- 项目综合排期 `/projects/:projectId/schedule`：统一展示镜头任务和资产制作分项任务，支持人员泳道、任务甘特、日/周/月缩放、首版基线、撞期、未排期池和授权管理人员改期；不得通过页面分组或拖动改变负责人。

- 版本详情 `/versions/:versionId`：归属 `reviews` 路由范围，展示真实版本信息和文件并通过受保护接口下载；响应通过只读 `productionTarget` 提供当前版本关联任务的制作依据，不在审核单表复制镜头或资产字段，也不要求调用者额外具备任务详情权限。
- 审核详情：先展示当前版本关联的审核依据。镜头视频完整展示制作内容、景别、机位、镜头运动、焦段、台词/对白、音效、色调参考和备注；资产图片展示资产类型、资产名称、制作分项、父资产/分项说明与备注；任务要求与主体说明不同时独立展示为“任务补充要求”。随后展示当前媒体、可选 A/B 参考、历史 open 问题与来源标注、制作人本版逐条处理说明、逐条确认、新问题创建和审核动作。

### 14.4 通用页面状态

所有列表和详情必须具备：加载中、空数据、请求失败、无权限、资源不存在、并发冲突和可控重试状态。不得只实现成功状态。

## 16. 数据一致性与并发规则

- 项目代号、集号、场次号、镜头号和资产名称必须有明确唯一约束；制作人昵称重复由 Excel 匹配歧义和人工选择处理。
- 一个镜头或资产制作分项最多一个正式任务，必须由数据库约束和服务层共同保证。
- 版本号分配、最终版本唯一性和审核动作必须具备并发保护。
- 前端写操作必须防重复提交；关键业务动作使用幂等键或等价机制。
- 资源更新应使用乐观锁或等价并发控制，过期页面不能静默覆盖他人修改。
- 创建版本、版本文件关系、平台文件业务引用、自动审核单和任务状态必须形成一致业务事务。
- NAS 与数据库跨资源操作必须有可重试、补偿和对账机制。
- 已提交版本、修改问题、逐版本处理说明、逐版本确认结果、审核动作和最终文件不能被普通 CRUD 覆盖。
- 项目创建、成员新增/恢复、项目角色变更和成员移除必须把 `sg_project_member`、相关 `sys_user_role` 增量、`sg_managed_user_role` 来源标记与领域审计作为一个数据库原子结果；任一步失败全部回滚。同步服务以事务内最新成员状态重算全部活动项目角色，并在同一用户内先授予仍需但缺失的映射，再按来源和依赖条件撤回不再需要的映射。
- 平台权限缓存失效在数据库提交后通过 `ApiGroup.USER_PERMISSION_MUTATION` 执行，禁止通过回滚已提交业务事务“恢复缓存”。任何受保护接口不得仅依赖可陈旧的角色缓存继续授权；目标用户已经打开的 SPA 必须刷新身份与导航快照。

## 17. 文件访问与安全规则

- 版本文件必须保留平台稳定 `fileId`，并同步业务引用，防止仍被版本使用时误删。
- NAS 路径访问权与平台文件下载权必须分别校验；项目成员身份不能自动等同于平台文件 ACL。
- 平台权限不能阻止用户绕过网页直接访问 SMB/UNC 共享。部署时必须通过 NAS、Windows/AD 或等价机制配置共享权限；如果整个部门共享对所有项目开放，系统必须明确接受“平台外可直接访问文件”的安全边界。
- 私有文件默认拒绝访问；只有拥有项目资源权限并通过文件授权的用户才能预览或下载。
- 项目成员可以只读查看所属项目的镜头、资产、任务、版本、意见和经授权文件；制作人员只可提交或重试本人任务，两类任务均须等待管理人员确认开工。
- 文件接口不得向前端泄露平台内部 `storage_key`、服务器本地路径或访问凭据。
- 统一全局搜索使用 `GET /shot-grid/search`，只返回当前账号有权读取且能打开详情的镜头、资产和正式版本文件；入口复用 `shotgrid:navigation:list`，各类结果同时校验相应列表权限与详情权限。响应只提供业务标题、项目归属和站内详情路由，不返回 NAS 物理路径。
- 下载文件名使用不可变业务文件名，并防止响应头注入。
- 永久删除文件或目录不属于普通项目操作；如未来实现，必须精确确认目标、权限、业务引用和恢复策略。
- NAS 对账至少应检查数据库引用、目标路径存在性、文件大小和 SHA-256 或等价摘要。

## 18. 非功能要求

### 18.1 可用性

- 桌面端为第一优先级，常用操作不得只在鼠标悬停时出现。
- 表单字段必须有明确标签、校验提示和错误定位。
- 搜索筛选条件应可清空；长列表采用服务端分页或虚拟化。
- 上传大文件必须展示真实进度、失败原因和可控重试，不得使用虚假进度。

### 18.2 性能

- 项目概览使用后端聚合或缓存，不得拉取全量镜头和资产到前端计算。
- 镜头、资产、任务、版本和审核列表必须分页。
- 图片缩略图和视频代理如未实现，不得直接用原始大文件伪装为已优化媒体。
- 文件大小上限、分页默认值和目标响应时间由部署环境压测后冻结。

### 18.3 可恢复性

- NAS 暂时不可用时必须失败关闭文件写入，并给出可诊断错误。
- 重试不能重复生成版本、审核单或业务文件。
- 数据库与 NAS 对账异常应进入管理员待处理清单。
- 备份恢复必须同时考虑 PostgreSQL、平台文件存储、NAS 项目目录和配置密钥。

### 18.4 可扩展性

- 项目类型使用代码与显示名称分离的字典设计，MVP 只启用 `AI影视短片`。
- 画幅使用受控枚举，新增画幅必须通过配置或版本化变更。
- 后续增加资产类型、外部审核、自动媒体处理或桌面客户端时，不得破坏现有版本不可变和审核绑定规则。

## 19. 核心验收场景

### 19.1 项目与 NAS

- 能以“罗刹夫人 / LCFR / 16:9 / AI影视短片”创建项目并指定至少一名项目管理人。
- 创建成功后，NAS 项目根目录及 `ASSET/Character`、`ASSET/Environment`、`ASSET/Prop`、`VIDEO` 均真实存在。
- NAS 不可访问、不可写、路径越界或目标冲突时，项目不会被显示为创建成功。
- 重复提交创建请求不会产生重复项目、成员或目录。
- 修改项目名称不会静默移动已存在的 NAS 根目录。

### 19.2 镜头闭环

- 项目管理人创建或导入集、场次和镜头；此时镜头状态为“未分配”，不存在制作任务。
- 项目管理人随后通过独立委派动作选择项目制作人员；系统第一次委派时只创建一个 `shot_video` 任务，后续改派更新同一任务。
- 集可在创建或导入时产生目录 Outbox；镜头和资产不在手工创建或 Excel 导入时建立对象目录。镜头也不把稳定内部 `shot_id` 写入路径，资产仅冻结稳定目录身份。
- 管理人员在线下确认资产齐备并确认开工后，尚无目录的镜头任务先进入“目录准备中”；NAS Outbox 成功创建冻结的 `{sceneNo:03d}_{shotNo:04d}` 目录后才进入制作中。随后上传合法视频，系统生成 `V001`、规范业务文件名和自动审核单。
- 项目管理人退回并填写意见，任务进入修改中；制作人员再次上传生成 `V002`，`V001` 仍可追溯。
- 项目管理人通过 `V002` 后，仅 `V002` 为最终版，任务和镜头均为已完成。

截至 2026-08-11，任务工作台和版本上传前端已完成隔离浏览器子集 E2E：fresh PostgreSQL 为 Alembic head `20260811_06` 且含 22 张 Shot Grid 表，Redis 使用隔离 DB 15，并通过真实平台账号登录；`/workbench` 返回本人任务 21 条、分页 20+1、keyword 过滤 1 条；`taskId=900001` 开始 HTTP 200，`lockVersion 0→1`。浏览器对 5663-byte `logo.png` 严格按 preflight 200 → private upload 200 → create 202 顺序调用，pending 刷新后由 current 200 恢复；显式 `allow_local_root=True` 本地 TEMP 适配器两阶段完成 `published→committed`、`attempt=1`，形成 `V001/pending_review`、任务 `lockVersion=2`、1 个 `auto_single` 审核单和 1 条正式文件引用。版本详情/受保护下载均 200，下载 5663 bytes 且 SHA-256 与源一致；console 0 error/0 warning；localStorage/sessionStorage 无认证 Token、`fileId`、幂等键、修改说明或 AI 参数，登录期间认证 Token 只存在 `Admin-Token` Cookie；logout 200 后 Cookie 清除，深链守卫及隔离资源精确清理均闭合。

该结论只表示“任务工作台与版本上传隔离子集 E2E PASS”。本地 TEMP 适配器只验证路径适配、摘要和两阶段发布算法，为夹具补齐的目录仅供逻辑路径预览；它不是正式 Windows/NAS 服务账号、UNC/SMB 或共享 ACL 证据。本旅程也未覆盖权限撤权负向、Range 206/416 真分段、MP4/MOV、failed/未知 create 浏览器负向、审核前端、`manual_batch`、codec/媒体轨/可解码性/转码、媒体派生或完整系统 E2E。

### 19.3 资产闭环

- 当前资产模板预检查明确显示 20 条总行和 12 个逻辑资产/20 个原始制作分项；第 6—8 行缺少制作分项为警告行。移除制作人列后，不再保留旧 v1 样表由复合制作人造成的 1 条错误。
- 资产导入以 `selectedRows[{sheetName,rowNumber}]`、短期 Token 和幂等键正式提交，刷新后父资产、未分配制作分项、自动匹配结果和 `not_created` 目录状态与数据库一致；导入不得创建目录 Outbox 或任务。
- 项目管理人创建 Character、Environment 或 Prop 资产及一个或多个制作分项，并为每个分项分配一名主制作人。
- 系统为每个制作分项只创建一个 `asset_image` 任务；缺少制作分项名称时仅可保存为未分配草稿，禁止分配、改派、开始任务和提交版本，补齐后才能进入制作流程。
- 列表、卡片和类型看板共享同一服务端结果；详情深链刷新后仍显示正确制作分项、后端动作和受保护缩略图。当前最新版本没有缩略图时不显示旧版本图片。
- 管理人员逐分项确认开工后，只有选中任务进入“目录准备中”，共享目录已成功则直接进入制作中；其他分项独立等待。系统按父资产锁复用唯一目录 Outbox，Worker 只推进已开工分项。制作中任务由当前制作人员上传合法图片，生成规范业务文件名、版本和自动审核单。
- 经多轮退回和提交后，每个制作分项只有一个最终版本；全部活动分项完成后资产聚合状态为已完成。

2026-08-11 的旧资产导入旅程曾按已废弃的 v1 预分配规则形成制作分项任务；它只保留为历史实现证据，不能验收当前“导入后全部未分配、任务数为 0”的新契约。新模板、预检、提交和后续独立委派链必须重新执行定向验证，未验证前不得沿用旧旅程的 PASS 结论。

### 19.4 权限与负向场景

- 非项目成员即使知道资源 ID，也不能读取项目数据或文件。
- 制作人员不能给自己分配其他任务、管理成员或执行最终审核。
- 镜头及资产制作分项开工只允许具备接口权限和管理范围的管理人员，制作人不能自行开工；版本提交/重试仍只允许当前受派制作人，管理员不得代操作。
- 镜头任务上传图片、资产任务上传视频必须被拒绝。
- 并发提交版本不会生成相同版本号；并发审核不会产生两个最终版本。
- 已提交版本文件、修改问题、逐版本处理说明、逐版本确认结果和审核动作不能被普通编辑接口覆盖。
- NAS 发布失败、数据库提交失败或网络中断后，系统不存在对用户可见的虚假成功版本。
- 项目创建、成员新增/恢复、项目角色变更和成员移除的浏览器网络记录中不得出现任何 `/system/*` 请求；前端只能提交 `director|creator` 并调用 Shot Grid 专用 API。
- 同一用户在两个项目中担任同一项目角色时，从其中一个项目移除不得撤回其受管平台角色；归档项目中的活动成员仍计算为历史只读依赖。退出最后一个依赖项目后，只有 Shot Grid 来源标记存在时才撤回。
- 预先由平台管理员分配且没有 `sg_managed_user_role` 来源标记的 `shotgrid_admin` 或 `shotgrid_creator` 不得被成员移除或改角删除。
- `shotgrid_admin`、`shotgrid_creator` 缺失、重复、停用、被删除或包含禁用权限时，角色选项 API 与相关项目/成员写入必须以稳定 503 错误失败关闭；不得使用 `*:*:*`、`shotgrid:project:all`、`system:*` 或存储根管理写权限绕过。
- 修改目标用户的项目角色后，服务端后续授权必须按数据库事实生效；目标用户已打开的 Shot Grid SPA 必须刷新或重新登录后再断言导航和按钮状态，不能把旧 Pinia 快照当成角色同步失败或已自动刷新。

### 19.5 项目概览

- 统计值与数据库内未归档镜头、资产、制作分项及其唯一任务状态一致。
- 待审核、修改中、完成数和整体完成度使用统一后端口径。
- 分页、筛选和视图切换不会改变项目总统计结果。

### 19.6 项目排期

- 镜头、资产和项目综合排期读取同一后端契约；日/周/月缩放与页面刷新不改变任务真实时间。
- 首次排期同时形成当前范围和不可变基线；后续拖动、缩放和精确编辑只改变当前范围，并保留完整结构化历史。
- 同人重叠先返回最新冲突，管理人员二次确认后可以保存；并发版本或冲突集合变化时旧确认不能穿透。
- 制作人员、已完成任务、归档/完成项目和失效目标保持只读；跨人员泳道拖动不能改派。
- 以不少于总计 5,000 个任务、当前窗口 2,000 个任务和 200 条人员泳道的基准验证分页、虚拟渲染、缩放和拖动，不能只以页面可打开或构建成功证明性能。

## 20. MVP 完成定义

只有同时满足以下条件，才能将 MVP 描述为完成：

1. 项目、成员、集、场次、镜头和资产可以在真实 PostgreSQL 中持久化；
2. 项目创建可在真实测试 NAS 或受控 SMB 测试共享上完成目录初始化；
3. 镜头和资产制作分项均完成“分配—制作—上传—版本—审核—退回—再提交—通过”闭环；
4. 业务文件真实落位且可由有权限的成员访问，命名和目录符合规则；
5. 权限、并发、重复提交、NAS 故障和非法文件等负向场景已验证；
6. 项目概览统计与真实数据一致；
7. 项目排期的基线、改期审计、权限、冲突确认、并发回滚、双视图和性能基准已完成对应验证；
8. 已执行后端、前端和真实浏览器 E2E 验收，并记录实际命令和结果。

源码存在、页面可打开、Mock 演示、静态检查通过、构建成功、服务启动成功或健康检查成功，都不能单独替代上述业务闭环验收。

## 任务分配、开工、预期时间与项目排期（2026-08-31 更新）

分配任务只确定制作人并核对制作内容。任务建立后，管理人员可以在排期视图提前设置或调整完整预期开始/结束时间；排期更新允许开始处于过去，以真实表达计划和延期。镜头与资产制作分项开工仍展示制作人、完整制作信息、优先级、时间及线下条件确认：已有当前排期时只读沿用，不因计划开始已过去而拒绝；尚无排期时才由开工窗口使用 Element Plus 日期时间范围选择器建立首次范围，此时新的开始不得早于当前操作时间，结束必须晚于开始。

管理员选择的时间只表达当前计划，不代表制作人实际作业时间，不延迟管理员确认后的开工放行，也不触发自动完成或阻断提前/逾期提交。首次完整时间冻结为基线，后续改期记录结构化历史。制作人的工作台及任务详情单独显示“时间：正常 / 临近结束 / 已延期”；结束前 24 小时内提醒优先处理，到期提醒尽快完成且仍可提交。已完成不再催办，历史无时间不伪造。系统实际完成仍以原审核通过流程为准。
