## 发现并修复的问题

### 人工审核单提交成功后报异步数据库错误

卢清华创建包含版本 79、80 的人工审核单时，事务实际已经提交，但响应构建读取了提交后过期的 ORM 主键，触发 `MissingGreenlet`。这会使用户以为创建失败并可能重复提交。

修复为提交前保存审核单主键，再使用普通整数查询响应。新增真实随机 PostgreSQL 测试，明确使用 `expire_on_commit=True`，验证成功响应及新会话回读。浏览器重新创建审核单 83，排序为 80、79，激活、归档均成功。修复前已创建的测试草稿保留，不删除历史。

### 永久清理重试的同类响应错误

检查同类路径发现，目标清理重试提交后直接序列化过期 ORM 对象，也可能出现“已进入待重试，但接口报错”。修复为提交前构造响应。真实随机 PostgreSQL 回归验证响应、计数重置和持久化状态；测试不启动清理 Worker，不访问 NAS，也不重试历史清理任务。

### HTTP 422、429 缺少合适提示

参数校验 422 原先可能显示“服务暂时不可用”。新增 422 参数提示和 429 限流提示，保留服务端明确业务消息及错误细节。增加两项单元测试，并用真实浏览器非法请求确认 422 显示“提交内容不符合要求，请检查填写内容”。

### 回滚缺少迁移版本兼容检查

手动回滚及发布失败自动回退原先只检查镜像存在，可能把旧应用切到不认识的新迁移版本。两处均增加目标镜像的 Alembic `current` 预检；失败拒绝切换，自动回退不兼容时停止后端并要求兼容版本或受控恢复。

特别注意：`ruoyi db current` 只读取数据库版本字符串，旧镜像也能成功返回 `20261116_44`，不能用作兼容检查。实际使用 `python -m alembic -c alembic.ini current`；旧镜像 `ed841878ec0c` 在专用恢复库上以 255 退出，明确无法识别 44；新候选镜像能够识别 44 head。四种手动/自动、允许/拒绝控制流测试通过，未执行真实发布或回滚。该检查不等同完整业务兼容性演练。

### 测试与格式修正

- CLI dry-run 断言对齐既有“当前 Python 的 `-m alembic`”实现，不再错误期待 PATH 中的全局 Alembic。
- 镜头参考资料测试在分配前验证省略、清空、恢复；分配后自动准备目录，明确验证普通编辑被拒绝，不再沿用旧的未开工假设。
- 制作周期 PostgreSQL 测试改用随机隔离数据库，不复用应用全局连接。
- Ruff 要求的五处 Python 格式修正，经 AST 对比不改变语义，包括两份历史迁移的纯格式调整。

### 管理端 npm 依赖锁定

干净镜像构建暴露管理端仍使用无锁的 `npm install`，持续解析依赖且存在版本漂移风险。既有锁文件虽然顶层与 package.json 一致，但 Linux `npm ci` 发现缺失 Rollup 及平台依赖；在独立 Node 22 Linux 容器中使用 `npm install --package-lock-only --ignore-scripts` 补齐，形成 1044 个包条目的 npm v3 锁文件。来源均为公开 registry.npmmirror.com，无本地链接或带凭据 URL。解除其 Git/Docker 忽略规则，将 CI 和生产镜像统一改为 `npm ci`，同步 README 与协作规则。未切换包管理器、未修改依赖声明，也未覆盖本机正在运行的 node_modules。锁文件不固定基础镜像或操作系统包，不能声称完整镜像位级可复现。
