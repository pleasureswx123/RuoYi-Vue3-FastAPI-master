# 项目成员多角色设计

日期：2026-10-12。状态：用户已确认并明确要求开始修改代码；代码已实现，验证与部署边界见实施目录中的验证记录。

## 1. 业务目标

同一用户在同一项目中仍只有一条成员记录，但可同时拥有“项目管理人（director）”和“制作人员（creator）”。添加和编辑均可多选，至少选一项；成员列表展示全部角色，重新编辑完整回显。双角色成员既可管理项目，也可被分配制作任务并提交本人任务的版本。

范围限于现有两个角色，不新增自定义角色、角色切换器或平台用户管理入口。

## 2. 已核对的现状与基座边界

- `entity/do/project_do.py` 的 `sg_project_member` 以 `(project_id, user_id)` 为复合主键，使用单值 `project_role`，成员状态为 `active/removed`。
- `entity/vo/project_member_vo.py` 的新增、编辑和响应使用单值 `projectRole`。`project_access_service.py` 的访问上下文及角色判断同样使用单值。
- 成员写入服务已在锁内检查最后一名管理人、活动任务、用户数据范围，并统一处理平台角色同步与审计。
- 平台角色映射为 `director → shotgrid_admin`、`creator → shotgrid_creator`，有来源标记的绑定才能由业务服务撤回。
- 前端 `ProjectMemberPanel.vue` 已使用 Element Plus Form 校验和 Select，但模型与提交均为单值。工作区该文件、相关文档已有用户修改，应保留。
- 本次属于兼容扩展；沿用 Controller → Service → DAO、Pydantic camelCase、ResponseUtil、现有权限依赖和异常响应，不新增返回协议。当前已有单值能力不能被描述成支持多角色。

## 3. 数据模型

新增 `sg_project_member_role`，每行表示一个成员的一项角色：

| 字段 | 类型与约束 | 用途 |
| --- | --- | --- |
| project_id | BIGINT，复合主键 | 项目 |
| user_id | BIGINT，复合主键 | 平台用户 |
| project_role | VARCHAR(20)，复合主键，限定 director/creator | 项目角色 |
| create_by | VARCHAR(64)，沿用创建审计约定 | 本次授权操作人 |
| create_time | 沿用 SHOT_GRID_DATETIME | 本次授权时间 |

通过复合外键关联 `sg_project_member(project_id, user_id)`，使用 RESTRICT；永久删除项目时显式先删除角色关系。按 `(project_id, project_role, user_id)` 建索引，支持管理人数、制作人选项和角色筛选。复合主键防止重复授权。

成员状态仍由成员表统一管理。移除成员时保留角色关系用于历史读取，但所有授权与平台绑定依赖必须同时检查成员 active；恢复成员时以本次明确提交的角色集合替换。角色关系不另设软删除或独立状态，撤销历史由领域审计保存。

保留原 `project_role` 列作为过渡兼容投影：有 director 时写 director，否则写 creator；新授权和查询一律使用关联表，不得从投影恢复权限。所有正式写入口必须在同一事务维护投影；禁止旧版本写服务与新版本混跑。

## 4. API 与前端

- 新增、编辑、初始成员使用 `projectRoles: ["director", "creator"]`；响应返回相同数组，固定 director、creator 顺序。
- 校验非空数组、合法枚举，重复项规范化去重。兼容旧请求 `projectRole` 为单元素数组；两种字段同时出现则拒绝，避免优先级歧义。
- 编辑仍允许原有非角色字段更新；未传角色不修改，显式 null 或空数组拒绝。兼容字段不是双角色的完整表示，前端全部切换至数组。
- 项目当前用户身份增加 `myProjectRoles`，访问上下文改为角色集合；旧单值响应仅作过渡展示兼容。全局管理员与非成员仍由 hasAllScope 表达，不伪造项目角色。
- 成员查询的单个 `projectRole` 筛选保留，语义改为包含该角色；使用 EXISTS 或等效方式避免成员、项目、任务列表重复及分页总数膨胀。
- 初始 directorUserIds 与初始成员列表按用户合并角色，不能让初始化双角色被覆盖。
- 添加、编辑使用 `ElSelect multiple`、数组 model、`ElFormItem prop` 和数组规则；显式按钮调用 validate，保留 loading、重复提交防护、失败提示、关闭清理。使用多个 ElTag 展示角色。
- 所有成员选择、制作人候选、项目身份标签与按钮判断同步迁移；制作人候选包含拥有 creator 的双角色成员。

## 5. 权限与业务规则

角色能力按集合合并，但平台接口权限、数据范围、活动成员状态、资源归属、项目状态和 allowedActions 仍需共同满足。不能因为多选角色绕过这些条件。

1. 新增 director 不撤掉 creator，不触发活动任务冲突；只有真正撤销 creator 才检查现有活动任务并要求先改派。
2. 撤销 director 或移除成员时，按仍包含 director 的活动成员计数，至少保留一名。
3. 开工仍由有管理身份及对应接口权限的人确认；版本提交和重试仍只能由具有 creator 且当前受派的本人执行。双角色不允许代别人提交。
4. 双角色按既有管理身份审核规则执行，本次不新增“禁止审核本人作品”限制；审计保留实际操作者。若后续需要制作与审核隔离，应独立提出业务规则。
5. 平台角色依赖按用户所有活动项目成员的角色集合求并集；撤销一个项目角色时，其他项目仍依赖的绑定不得撤回。无来源标记的用户角色不得删除。
6. 成员变更、角色集合、兼容投影、平台增量绑定和领域审计处于同一事务。沿用目标用户锁、项目锁及锁内重新授权顺序；并发移除最后管理人必须串行复核。
7. 成功提交后沿用 USER_PERMISSION_MUTATION 缓存失效。已有 SPA 身份刷新遵循当前机制，不承诺跨客户端实时推送。

审计记录角色变更前后完整集合，包括新增、恢复、编辑和移除。文件访问、审核、任务、排期、统计、项目永久删除以及平台角色保护与对账均纳入单值判断排查范围，避免只迁移成员接口。

## 6. PostgreSQL 迁移与交付

提供接续仓库实际 Alembic head 的新 revision，并同步 PostgreSQL 初始化 SQL；不使用文档中历史 head 推定当前版本。本次只承诺 Shot Grid 的 PostgreSQL 路径。

迁移为所有已有成员（含 removed）按原单值回填一条角色关系，不变更用户任务、NAS 路径、成员状态或平台权限包。检查每条成员记录至少存在一条有效角色记录。

发布前备份，暂停旧业务写入，执行迁移并统一更新后端和前端，再开放写入。保留旧字段不能支持旧应用安全写入双角色数据。

降级必须检查所有成员，包括已移除成员；若存在多角色成员则明确拒绝，禁止静默丢失角色。只有全部成员均为单角色时才允许回填旧列并删除关联表。正式部署与真实环境数据迁移不在本次开发自动执行范围。

实施时同步后端与 Shot Grid 最近作用域 AGENTS.md，以及 `shot-grid-frontend/docs/领域模型与API契约.md`；区分旧事实与新契约，保留无关已有改动。

## 8. 设计选择

采用关联表而非逗号字符串或组合角色，保证枚举、外键和唯一性可验证，避免组合数量膨胀。保留短期单值兼容投影可减少已有读取客户端的立即破坏，但安全判断必须一次迁移完整；后续删除兼容字段需单独发布契约变更。
